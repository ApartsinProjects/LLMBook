The Vertical-Slice Pattern in Depth

Section 44.2
Big Picture

Section 44.1 introduced the 80/20 cuts: what an LLM MVP is allowed to skip. This section goes deep on the single most important pattern for scoping what's left: the vertical slice. A vertical slice is the thinnest possible end-to-end path through your system that delivers user value. Building a thin slice through every layer beats building 50 percent of every layer in isolation, and the gap between those two outcomes is the difference between shipping in five days and shipping in five months. The pattern looks obvious in retrospect and is surprisingly hard to enforce in practice.

1. Why Horizontal Scope Fails

The classic MVP failure mode is horizontal scope: the team builds half of every layer (data ingestion, retrieval, model orchestration, UI, authentication, billing) and ships none of them end-to-end. Three weeks in, the product manager asks for a demo and discovers nothing actually works because the seams between layers have not been wired up. The team scrambles to integrate, discovers each layer was designed in isolation with incompatible assumptions, and another month evaporates.

The pattern is so consistent that it has a name in software-engineering folklore: the "Christmas tree" anti-pattern, where every team member has decorated their own branch beautifully and nobody hung it on the tree. ThoughtWorks' "Walking Skeleton" essay from the early 2000s named the right alternative two decades ago: get a thin, ugly, end-to-end version working first, then thicken it.

The pattern is twice as dangerous in LLM products because each layer of the stack has its own failure modes that only surface in integration. The prompt that worked beautifully in your notebook produces different output when called from a production service. The retrieval that scored 95 percent on your offline eval set drops to 70 percent when real users phrase queries differently. The fancy streaming UI breaks the moment your auth middleware adds a 400ms round-trip. You cannot find any of this until the slice runs end to end.

2. The Five Layers of an LLM Vertical Slice

A vertical slice for an LLM product has a stable shape. Each layer is as thin as possible; the discipline is to refuse to thicken any layer until all five exist. The thinnest slice has exactly these five components:

  1. One input type. Pick the single most common shape your users will provide: a pasted block of text, an uploaded PDF, a Slack message. Reject anything else with a clear error.
  2. One LLM capability. Pick exactly one of the seven from Section 40.3: extraction, RAG, classification, drafting, agentic action, schema translation, or code completion. Resist combining them.
  3. One output format. Structured JSON, a markdown summary, a single decision label. The format is fixed in the spec and does not vary by input.
  4. One user-visible surface. A web form, a Slack slash-command, a CLI. The surface does not need to be polished; it needs to be reachable by a real user.
  5. One feedback signal. Thumbs up/down, a one-line text box, or a follow-up survey email. Without this signal, you cannot tell whether the slice worked.

Each layer is intentionally minimal. The point is not to be cheap; it is to be measurable. When something breaks, you know exactly which layer to look at. When a user complains, you know exactly which step produced the complaint. When the hypothesis fails, you have an unambiguous reading because there is only one path through the system.

Practical example: a 2025 legal-tech MVP shipped in five days

A four-person team at a 2025-launched legal-tech startup wanted to validate "preparers will pay for an AI assistant that drafts client-reply emails." The original spec called for OCR on scanned letters, multi-document reasoning across full case files, integration with three case-management platforms, multi-tenant auth, and a polished React UI. Estimated time: ten weeks.

The vertical slice they shipped instead: a single web page where the preparer pastes the text of one client email and gets back a structured draft reply. No OCR, no integration, no auth beyond a shared link. Built in five days using a Cursor + Claude Code workflow (see Section 43.3). In week two of the pilot, the team learned preparers actually wanted "what should I reply" rather than the originally specified "what documents do I need." The ten-week spec would have built the wrong product. The five-day slice cost a week and prevented the wrong-product disaster. The product reached \$1M ARR by mid-2026 with the corrected scope.

3. The Discipline That Holds the Slice Thin

The hardest part of the vertical-slice pattern is not the engineering. It is resisting the constant temptation to thicken layers before they all exist. Three disciplines, applied weekly, hold the line.

The "freeze list." On day one, write down the list of features that are explicitly out of scope. Pin it visibly. When someone proposes a feature in standup, check the list. If it is on the list, the answer is no. If it is not on the list, ask whether it belongs on the list. Most "just one more feature" requests die in this conversation because the team did not really want them; they were just trying to be helpful.

The "single demo path." The slice has exactly one user journey from start to finish. Every demo, every test, every pilot interaction follows the same path. If a stakeholder asks "what if the user does X instead," the answer is "out of scope for v1; we will know if that's needed after the pilot." The slice exists to test one hypothesis, not three.

The "five-day rule." If any single layer takes more than five days to build the thinnest possible version, stop and ask why. The most common reason is that the layer is doing more than the minimum. The auth layer should be a shared link. The UI layer should be a Streamlit page. The data layer should be a JSON file. Five days for any one layer is a signal you have crept past minimal.

Warning: the "but it's almost done" trap

The temptation to thicken a layer is most acute when it is almost finished. "We have 80 percent of the OCR working; let's spend two more days and ship it." Resist. The remaining 20 percent of OCR is the 80 percent of the work. If OCR is not in your slice, do not start it. Worse, every thickened layer makes the seam-failure investigation harder: when the slice misbehaves, you now have to rule out OCR before looking at the LLM. Each additional feature in v1 is a hypothesis you cannot test cleanly.

4. When the Slice Reveals the Wrong Hypothesis

The most valuable outcome of a vertical slice is not "the product works." It is "the hypothesis was wrong, and now we know which one." A slice that works exactly as designed is a partial validation; a slice that surprises you is much more informative, because surprise is where learning lives.

Three patterns of productive surprise recur across MVP retrospectives:

  • The user wanted a different output. The slice produced output X; users edited it to look like output Y. Y is what you should have been producing. Update the slice (a small change), re-pilot.
  • The user wanted a different input format. The slice accepted Y; users kept trying to paste X. X is what you should have been accepting. Add minimal X support, re-pilot.
  • The user wanted a different capability entirely. The slice did extraction; users wanted summarization. This is the largest surprise, and the right response is usually a full re-slice rather than a tweak. The hypothesis was wrong at the capability level, which is one level up from "the slice was wrong."

All three surprises are cheap to recover from if the slice was thin enough that you can re-build it. The same surprises in a horizontal-scope project would cost months because the team has invested in the wrong assumptions across every layer. The thin-slice discipline pays for itself precisely in these moments.

The vertical slice is a sensor, not a product

A vertical slice's job is to produce information about what the product should be. It is not the product. Treating the slice as the product is the most common psychological error in MVP work; teams over-invest in polishing it because they cannot tell themselves "this is throwaway." The right framing is borrowed from astrophysics: the slice is a telescope. You point it at the universe to learn something, and then you decide what to build based on what you saw. Telescopes are valuable; nobody confuses them with the stars.

Key takeaway
  • Horizontal scope (50 percent of every layer) fails because seams break in integration; vertical slices (100 percent of one path) succeed because they ship.
  • The five layers of an LLM slice: one input, one capability, one output, one surface, one feedback signal.
  • Discipline holds the slice thin: the freeze list, the single demo path, the five-day rule.
  • The most valuable slice outcome is a productive surprise about user behavior, not a successful demo.
  • Treat the slice as a sensor for learning, not as the product itself.
