Prototyping via Vibe-Coding

Section 68.1

"The best code is the code you never had to write yourself. The second best is code you wrote with an AI that understood your codebase."

Pip, Vibe-Coding AI Agent
Big Picture

"Vibe-coding" is the shorthand that emerged in 2024 to 2025 for a new kind of programming, where the developer describes the desired behaviour in natural language and an LLM-driven tool writes, modifies, and tests the implementation. The term is informal, and a little tongue-in-cheek, but the underlying shift is real and economically significant. The build-test-fix cycle that used to take minutes (or hours) now takes seconds. For prototyping an LLM product, vibe-coding compresses the time between idea and running code to the point where the bottleneck is no longer typing speed but decision-making and taste. This section maps out what vibe-coding is in 2026, when it pays off and when it does not, the major tool families (Cursor, Claude Code, Cline, Copilot, Aider, and the no-code builders), and the mistakes that consistently turn fast prototypes into expensive technical debt.

Prerequisites

This section assumes familiarity with the modern LLM landscape from Section 7.1 and the prompt engineering patterns from Section 12.1. Understanding the code-agent architectures from Section 26.3 is helpful, because under the hood every vibe-coding tool is a code agent with carefully chosen tools and context limits.

68.1.681.1 What "Vibe-Coding" Actually Means

The phrase entered widespread use after a 2025 post by Andrej Karpathy describing a workflow where he "fully gave in to the vibes" and let the model write code based on intent rather than careful specification. The catchy framing stuck. Strip the vibes, though, and what is left is a precise set of practices: short natural-language instructions, an LLM that reads the relevant context (files, errors, tests), generated code edits, and immediate feedback from a running system. The cycle repeats every few seconds.

Three properties distinguish vibe-coding from older "AI-assisted" workflows like autocomplete:

  • The model edits files, not single lines. Where 2022-era Copilot wrote one line at a time, modern tools edit whole files (or multiple files at once) in response to a single instruction. This matters because most useful edits cross file boundaries.
  • The model reads and reasons about the entire repo. Tools like Cursor, Claude Code, and Cline can pull in any file they decide is relevant, run tests, read errors, and iterate. The 2026 versions also call out to documentation servers, package indexes, and the developer's own shell.
  • The developer's role shifts from writing to reviewing. The interesting work is no longer "write the function," it is "did this function do what I meant?" Code review becomes the primary cognitive activity, with code generation as the supporting infrastructure.
Key Insight

Vibe-coding is leverage, not magic. A developer who knew what good code looks like before the LLMs arrived will ship 5 to 10 times faster with them. A developer who did not know will ship code that runs but cannot be safely changed. The skill being amplified is taste, not typing. Hire (and become) the kind of developer who can tell, in 30 seconds of reading, whether the LLM's diff is right or wrong. Everything else is downstream of that.

68.1.681.2 When Vibe-Coding Pays Off (and When It Doesn't)

The temptation, once a team has internalised the speed of vibe-coding, is to use it for everything. This is a mistake. The economics are wildly different depending on what you are building. The following table is the rough decision map most teams converge on after a few months of practice.

Table 68.1.1: When Vibe-Coding Helps Most vs. Least (as of 2026).
Task shape Vibe-coding leverage Why
One-off prototype to test a hypothesis Extremely high (5 to 20x) Throwaway code; speed dominates. Quality matters less than learning.
Glue code between APIs High (3 to 10x) Boilerplate is the bulk; LLM knows the patterns; review is fast.
Standard CRUD apps High (3 to 10x) Well-trodden territory; many examples in the training data.
Refactors within a known idiom Medium (2 to 5x) Models excel at "make this consistent" but can miss semantic invariants.
Novel algorithm or distributed systems work Low (1 to 2x) Subtle correctness; few comparable examples in training data; bugs are silent.
Performance-critical paths Low to medium Models suggest "fast-looking" code that often has the wrong asymptotics.
Security-sensitive code Use with caution Models reproduce known anti-patterns from the internet; auth code in particular.

The pattern is consistent: vibe-coding is wonderful when the task has been done a million times in the training data and the cost of being wrong is small, and weak when the task is novel, subtle, or expensive to misjudge. For prototyping an LLM product, almost everything you build in the first 30 days falls into the "high leverage" rows. After product-market fit, the proportion shifts and the team has to learn when to slow down.

68.1.681.3 The Build-Test-Fix Cycle Compressed to Seconds

The economic core of vibe-coding is not that the LLM types faster than a human (it does), but that the inner loop of "write code, run it, see the error, fix it" has collapsed from minutes to seconds. The mechanics of a modern vibe-coding session look like the following.

  1. State the intent in plain English. "Add a `/health` endpoint that returns 200 OK with the current Git SHA." The instruction is short. Long instructions are usually a sign that the developer has not yet decided what they want.
  2. The tool selects the relevant context. It reads the router file, the existing endpoints, the deploy config. The developer does not paste files into a chat; the tool decides what it needs.
  3. The model proposes a diff. Sometimes one file, sometimes ten. The diff is shown side-by-side with the original.
  4. The developer accepts, edits, or rejects. Modern tools default to "accept all" with a per-hunk override. The review step is fast because the diffs are short and idiomatic.
  5. The tool runs the tests (or the dev server, or the linter). Errors come back. The model fixes them. The developer rarely sees the intermediate failures unless they choose to.
  6. Loop until done. The whole cycle, from intent to passing tests, is often under 30 seconds for small changes.
Real-World Scenario: From Empty Folder to Working Prototype in a Morning

Who: A product manager (not an engineer) at a consumer health startup.

Situation: The PM wanted to test whether users would accept an AI assistant that summarised lab test results in plain language. The engineering team was busy with the main product.

What happened: Using Claude Code in a fresh folder, she described the goal: a Streamlit app, file upload for a PDF lab report, an LLM call that produced a plain-language summary, and a basic thumbs-up/down feedback widget. Three hours later there was a working prototype on a public URL. By the end of the day, five colleagues had tested it and the team had a clear thumbs-up signal worth investing engineering time in.

What this is not: A production system. There was no authentication, no PII handling, no observability, no eval suite. It was a prototype whose job was to test the hypothesis. The engineering team picked up from there with the spec in hand.

Lesson: Vibe-coding lets non-engineers build the prototype that justifies hiring an engineer. The 2026 version of "if you can describe it, you can ship a prototype of it" is closer to literal truth than it has ever been.

68.1.681.4 The Tool Landscape in 2026

The vibe-coding tooling space has consolidated into a few clear families. The differences matter mostly for team workflows and security postures; the underlying model capability has converged across the leaders.

  • GitHub Copilot. The original, now integrated as both inline completion and a chat surface across major IDEs. Strongest in enterprises that already live in GitHub. Less aggressive at multi-file edits than the agentic tools.
  • Cursor. A fork of VS Code with first-class agentic editing. The "Composer" workflow is the canonical reference for cross-file vibe-coding in an IDE. Strong indexing of the repo. Popular with solo devs and small teams.
  • Claude Code. Anthropic's terminal-based agent. Lives in your shell, edits files, runs commands, and reads the project's CLAUDE.md for conventions. Strong for tasks that span the editor and the shell (deployment scripts, CI debugging, ops work).
  • Cline (formerly Claude Dev). An open-source VS Code extension that runs as a code agent. Notable for transparency: every tool call is visible, every diff is reviewable, every shell command requires approval.
  • Aider. A command-line tool that pairs vibe-coding with strict Git integration. Every model edit becomes a commit. Excellent for developers who want a tight audit trail and easy rollback.
  • Bolt, v0, Lovable. The full-application generators. Single-prompt-to-deployed-app, with the output running in a managed sandbox. Trade depth for breadth. Excellent for prototypes that need a polished UI, weaker for code you intend to maintain over years.

The right choice depends on what you are optimising for. Solo prototyping in a notebook: Cursor or Claude Code. Engineering team workflow with strict review: Copilot or Cline. Non-engineer building a demo: Bolt or v0. Audit-trail-heavy work: Aider. Section 68.2 goes deeper into the architectural patterns these tools share, including Fill-in-the-Middle, the system-prompt structure of code agents, and the security model of letting an LLM run shell commands on your machine.

68.1.681.5 Mistakes to Avoid

The patterns below are the ones that consistently turn a fast prototype into a slow, fragile system. They cost teams weeks of debugging that the speed of vibe-coding should have saved.

  • Accepting diffs you do not understand. The model will happily generate code that looks plausible and is subtly wrong. If you cannot explain in one sentence what a change does, do not accept it. The 2026 versions of vibe-coding tools make rejection nearly free; use it.
  • Skipping tests because "the model will catch the bugs." It will not. Generative tools optimise for plausible code, not correct code. A small set of fast tests, written as part of the vibe-coding cycle, catches the regressions the model itself introduced. Aider, Cursor, and Claude Code all integrate test runners; turn them on.
  • Letting the model own architecture. Models are excellent at idiomatic local edits and terrible at architectural taste. They will happily produce a project with six different state-management libraries, four logging frameworks, and three database clients if you ask in three different sessions. Lock the architecture in a short design doc (or a CLAUDE.md equivalent) and reference it in every session.
  • Vibe-coding security-critical code without an extra review pass. Authentication, authorization, cryptography, and payment flows are full of subtle pitfalls that models reproduce from the long tail of insecure tutorials they were trained on. Read every line of generated auth code, twice. The OWASP Top 10 is not less relevant in the vibe-coding era; it is more relevant, because the volume of generated code has gone up.
  • Letting prototype code go to production without a rewrite. The fastest path is rarely the most maintainable one. The prototype's job is to prove the hypothesis; once proven, expect to throw 30 to 70 percent of the code away and rebuild for clarity, observability, and the quality budgets you committed to in the spec. Teams that skip this step end up paying for it in incident-response time for years.
Warning: The "Lovable Production" Trap

Single-prompt application builders make it easy to ship a real-looking app the same morning you had the idea. Users sometimes treat these prototypes as production systems. They are not. The generated code is fine for a demo, but it usually skips error handling, request validation, rate limiting, observability, and the most basic security headers. If your "Lovable prototype" suddenly has paying customers, schedule an engineering rewrite before the first incident; do not wait for the second.

68.1.681.6 Vibe-Coding's Place in the Idea-to-Product Pipeline

For the rest of Part X, vibe-coding is the engine that compresses everything between "we have a hypothesis" and "we have something for users to push back on." The ideation chapter (Chapter 67) ends with a one-paragraph hypothesis; the spec chapter (Chapter 67) turns it into a contract; the MVP chapter (Chapter 68) asks for a vertical slice in 30 days. None of those timelines are realistic without vibe-coding, and all of them become realistic with it. The cost of trying an idea has fallen so low that the limiting factor is no longer engineering capacity; it is the quality of the questions you are asking.

That shift has implications for how product teams organise. The PM who can vibe-code a prototype is no longer waiting on an engineer to find out if an idea has legs. The engineer who can review a vibe-coded diff and improve it is worth far more than one who only writes code from scratch. The 2026 LLM product team is more horizontal, more visual, and more focused on the loop between user feedback and code change than any version that came before it.
