71.2.712.1 Web frameworks for AI apps

Install Python deps with uv (Astral, 10-100x faster than pip and the modern default). The 2026 production stack has shifted: enterprises moved heavily to Next.js + Vercel AI SDK for shipping AI products; Streamlit and Gradio still dominate notebooks and internal demos but are no longer the production default.

  • Next.js + Vercel AI SDK: the dominant React stack for AI products in 2026 production.
  • FastAPI: Python backend default.
  • Streamlit and Gradio: rapid demo UIs and internal tools; not the right pick for customer-facing production where Next.js has won.
  • Chainlit: chat-app-specific framework.
  • convex: real-time database with first-class TypeScript types; modern backend for AI products.
  • inngest: durable workflows for background AI jobs.
  • trigger.dev: background job queues with AI-friendly retries.
  • Mastra (TS): agent framework purpose-built for SaaS.
  • Clerk and WorkOS: auth providers (often missing from 2024-era guides).
  • livekit-agents and vapi: real-time voice-agent libraries; the right pick when your product is voice-first.
FastAPI + OpenAI streaming via Server-Sent Events
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from openai import OpenAI

app = FastAPI()
client = OpenAI()

@app.post("/chat")
def chat(prompt: str):
    def gen():
        with client.chat.completions.stream(
            model="gpt-5", messages=[{"role":"user","content":prompt}]
        ) as s:
            for event in s:
                if event.type == "content.delta":
                    yield f"data: {event.delta}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")
Code Fragment 71.2.1: Implementation of chat, gen.

That is the entire production pattern for streaming chat: server-sent events, OpenAI streaming context manager, one route. Hook into Vercel AI SDK's useChat on the frontend and you have a complete streaming chat app in under 50 lines of code total.

71.2.712.2 Deployment

  • Vercel (Vercel, 2015) is the Next.js-first hosting platform that also publishes the Vercel AI SDK and runs the Vercel AI Gateway (a managed LLM proxy with caching and routing). Its objective is to make Next.js + LLM apps deployable with one push, which matters because AI-product time-to-market is competitive. Pick Vercel when your stack is Next.js or React; for Python backends, Fly or Render are better backends.
  • Cloudflare Workers AI (Cloudflare, 2023) is the edge-inference platform running small LLMs at Cloudflare's 300+ POPs. Its objective is to provide low-latency inference globally without managing GPUs, which matters when latency below 100 ms to any user is a product requirement. Pair with Cloudflare Containers (2025) for edge agent sandboxes. Pick Workers AI for latency-critical edge inference; for top-quality LLMs, central-cloud APIs still win on raw capability.
  • Fly.io (2017), Render (2019), and Railway (2020) are PaaS platforms suited to AI apps with backends in any language. Their objective is to make container deployment a git-push workflow without managing Kubernetes, which matters for small teams. Pick Fly.io for global multi-region deployments, Render for the simplest Heroku-equivalent experience, Railway for the cleanest dev-team UX. All three handle Python + GPU backends in 2026.
  • Modal (Modal Labs, 2021) is the serverless Python compute platform with first-class GPU access, ideal for AI workloads that need GPUs intermittently. Its objective is to give you GPUs (any size, on-demand, 200ms cold start) without managing them, which matters when your workload's GPU usage is bursty. Pick Modal for bursty GPU workloads (fine-tunes, batch inference, occasional generation); for steady traffic, dedicated GPU rentals are cheaper.
  • Groq (Groq, 2016) is the LPU (Language Processing Unit) inference platform with sub-100ms time-to-first-token for popular open models. Its objective is the fastest possible inference latency, which matters for voice-AI, interactive agents, and any product where latency is the differentiator. The core concept is custom silicon optimized for tensor-streaming language-model inference. Pick Groq for lowest-latency model calls; for highest-quality models, Anthropic and OpenAI lead.

The broader 2024-25 "edge AI" trend extends beyond a single bullet: Workers AI, Vercel AI Gateway, and Groq together represent a deployment pattern where inference happens close to the user and the orchestration layer stays serverless. For prompt caching as a cost-optimization technique, see Section 14.4; it belongs in the product-tooling stack and is widely under-used.

For desktop AI applications, the 2025 stack shifted from Electron to Tauri 2 + Rust for smaller binaries, better resource use, and less battery drain.

Reproducibility and CI/CD for ML

Reproducibility is the ability for someone else (or your future self) to re-run your experiment and get the same results. In ML, achieving perfect reproducibility is difficult due to floating-point non-determinism on GPUs, but you can get very close. Code Fragment I.4.1 below puts this into practice.

The Reproducibility Checklist

  1. Pin all dependencies. Use pip freeze > requirements.txt or conda env export > environment.yml. Record the exact PyTorch, Transformers, and CUDA versions.
  2. Set random seeds. Fix seeds for Python, NumPy, and PyTorch at the start of every script: 
    # PyTorch implementation
# See inline comments for step-by-step details.
import random, numpy as np, torch
random.seed(42)
np.random.seed(42)
torch.manual_seed(42)
torch.cuda.manual_seed_all(42)
    Code Fragment I.4.1: Fixing random seeds for Python, NumPy, and PyTorch (including CUDA) to ensure reproducible training runs across executions.
  3. Version your data. Use DVC or record dataset checksums (SHA-256 hashes) in your experiment logs.
  4. Log everything. Hyperparameters, hardware info, git commit hash, and the exact command used to launch training.
  5. Use configuration files. Store hyperparameters in YAML or JSON files rather than command-line arguments. Version these files with Git.
  6. Record hardware info. GPU model, driver version, and CUDA version can all affect results. Log them automatically: 
    # PyTorch implementation
# See inline comments for step-by-step details.
import torch
config = {
    "gpu": torch.cuda.get_device_name(0) if torch.cuda.is_available() else "CPU",
    "cuda_version": torch.version.cuda,
    "pytorch_version": torch.__version__,
}
    Code Fragment I.4.2: Capturing hardware metadata (GPU model, CUDA version, PyTorch version) in a dictionary for inclusion in experiment logs.
Fun Fact: The Reproducibility Crisis

A 2022 survey found that only 30% of ML papers included enough information to reproduce their results. The ML community is gradually improving through tools like DVC, W&B, and Hugging Face Model Cards, but the gap between "it works on my machine" and "anyone can verify this" remains wide. Being rigorous about versioning and logging puts you ahead of most practitioners.

Big Picture: Collaboration as Infrastructure

Git, DVC, and the experiment-tracking platforms covered in Appendix J are not overhead; they are infrastructure. A team that invests in these tools early spends less time debugging "what changed?" and more time making progress. For solo practitioners, these same tools serve as a conversation with your future self: three months from now, you will not remember which learning rate produced that promising result unless you logged it.

MLOps Plumbing: GitHub Actions for Model Deployment

The reproducibility checklist above gets you to a state where every result is rebuildable from Git history. The next step is automation: a CI/CD pipeline that pulls a registered model version, runs validation gates, builds a serving image, and rolls it out. The example below uses GitHub Actions to deploy a model that was registered with MLflow or W&B (see Section 19.2 (Libraries & Frameworks) for the registry side: how aliases and validation gates are defined on the tracker).

# .github/workflows/model-deploy.yml
# Triggered manually with a model name and version; runs validation,
# builds a Docker image, and rolls out to staging.

on:
  workflow_dispatch:
    inputs:
      model_name:
        description: "Registered model name"
        required: true
      model_version:
        description: "Version to deploy"
        required: true

jobs:
  validate-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install dependencies
        run: pip install mlflow boto3
      - name: Run validation gates
        run: |
          python scripts/validate_model.py \
            --model-name ${{ inputs.model_name }} \
            --version ${{ inputs.model_version }}
      - name: Build serving container
        run: |
          mlflow models build-docker \
            -m "models:/${{ inputs.model_name }}/${{ inputs.model_version }}" \
            -n "llm-serving:${{ inputs.model_version }}"
      - name: Deploy to staging
        run: |
          python scripts/deploy_to_k8s.py \
            --image "llm-serving:${{ inputs.model_version }}" \
            --environment staging
Code Fragment I.4.3: A GitHub Actions workflow that consumes a model version from the registry, runs validation, containerizes it via MLflow, and rolls out to a Kubernetes staging cluster. The workflow is triggered manually (workflow_dispatch); in mature setups it triggers automatically when a new version is tagged candidate in the registry.

The validate_model.py script that the workflow calls is a thin Python wrapper around the tracker's API. It loads the candidate version, runs the same accuracy / safety / latency gates that K.4 defines in validate_and_promote(), and exits non-zero on any failure, which stops the GitHub Actions job before the container is built. This keeps the policy (what counts as a "promotable" model) in one Python file that both the registry-promotion path and the CI/CD path call into.

# scripts/validate_model.py
import argparse
import mlflow
import sys

def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--model-name", required=True)
    parser.add_argument("--version", type=int, required=True)
    args = parser.parse_args()

    model_uri = f"models:/{args.model_name}/{args.version}"
    model = mlflow.transformers.load_model(model_uri)

    # Reuse the same gates defined in the registry validator (K.4 M.4.5).
    accuracy = run_eval_suite(model)
    if accuracy < 0.90:
        print(f"FAIL: accuracy {accuracy:.3f} < 0.90")
        sys.exit(1)

    print(f"PASS: accuracy {accuracy:.3f}")

if __name__ == "__main__":
    main()
Code Fragment I.4.4: The validate_model.py helper invoked by the GitHub Actions workflow. It exits non-zero on a failing gate, which causes the workflow job to fail before any container is built or deployed. Add safety and latency checks alongside the accuracy gate to match the registry-side validate_and_promote() in K.4.

The CI/CD pipeline treats model deployment like software deployment: each model version is validated, containerized, and promoted through environments (staging, then production). Rollbacks are straightforward: point the registry alias back to the previous version, then rerun the workflow against that version number. Treat the GitHub Actions YAML and the validator script as code that lives in your repo under .github/workflows/ and scripts/, versioned alongside your training code.

Collaboration Toolkit Summary

  • Start every ML repo with a thorough .gitignore that excludes model weights, datasets, and cache directories.
  • Use Git LFS for the rare large files that must be versioned, and DVC for datasets and model checkpoints.
  • Stamp every run with git_sha in the tracker config (Section I.3); for milestone runs, drop a run/<id> Git tag.
  • Pin dependencies, set random seeds, use config files, and log hardware info for reproducibility.
  • Wire model promotion into GitHub Actions so deployment is a code-driven event tied to a registry alias.
  • Treat collaboration tooling as an investment, not a cost. It compounds over every experiment you run.
