The Bet-My-Money Test and Capability Mapping

Section 67.3
Big Picture

Brainstormed ideas are cheap; funded engineering quarters are expensive. The bet-my-money test is the single sharpest filter that converts a long list of "ideas" into a short list of "candidates worth a 30-day MVP." Then, once a candidate passes the filter, you have to map its shape onto a specific LLM capability, because different capabilities have wildly different cost curves, latency profiles, and failure modes. Mis-mapping is the most common reason an LLM project misses its budget by 3x.

67.3.1 The Three Uncomfortable Questions

The bet-my-money test asks one question with a particular framing: would you personally invest $50,000 of your own savings in this product? Not your employer's money, not your investors' money, your own. The framing matters because it forces you to imagine real downside, which is exactly what brainstorm-style ideation suppresses. Behind the framing sit three concrete sub-questions you have to answer honestly before allocating engineering time.

Would the user actually pay for this? Not "would they say nice things in a survey" but "would they hand over a credit card or a contract?" If the target user already has a budget line for an intern, a consultant, or a software license doing this work, willingness to pay is established and you are essentially competing for an existing budget. If the user would need to be convinced this is a category they should spend on, you have a marketing problem on top of an engineering one, and most LLM products that take this path die not from technical failure but from sales-cycle starvation.

Can you describe the failure mode in one sentence, and is the failure recoverable? "The model writes a wrong summary and the analyst notices in ten seconds" is recoverable. "The model approves a fraudulent transaction and the bank loses $50k" is not. If you cannot describe the failure mode crisply, you have not thought about it hard enough; if the failure is unrecoverable, you have just admitted you are building a Tier-4 product and should budget accordingly (see the risk-tier framework in Section 67.4).

Is there a moat besides the prompt? A 50-line OpenAI API wrapper is not a defensible product in 2026. The moat has to come from somewhere: proprietary data, distribution channels, deep workflow integration, regulatory compliance, brand trust, or switching costs. If your honest answer to "what stops a competitor from rebuilding this in a weekend" is silence, go in with eyes open about how long you have before commodification.

Practical example: the $50k question that killed a feature

A 2025 case from a mid-sized fintech: a product team wanted to ship an "AI-powered budgeting coach" feature inside their consumer app. The team had three engineers ready to start. The CTO ran the bet-my-money test in a 30-minute meeting. The user-would-pay question failed first (the feature was free, attached to a free app, with no clear premium tier). The failure-mode question failed second (a budgeting suggestion that pushes a user into overdraft has real consumer-finance regulatory exposure). The moat question failed third (every competitor was shipping the same feature). The CTO killed the project before any code was written. The engineers were redirected to a fraud-triage internal tool with crisp willingness-to-pay (it replaced a $1.2M/year vendor contract) and clear ROI. The bet-my-money test paid for itself in one meeting.

67.3.2 Mapping Problem Shapes to LLM Capabilities

Once a candidate problem survives the bet-my-money test, the next step is mapping it onto a specific LLM capability. Different capabilities have different production characteristics: extraction is fast and cheap, agentic workflows are slow and expensive, RAG sits in the middle with the additional cost of a retrieval index. Mis-mapping costs you weeks, not hours, because you only discover the mismatch when the first pilot users hit your latency or your bill.

The capability menu has stabilized in 2026 around seven patterns. Each one has a different "cost-quality-latency triangle" and a different default failure mode. The table below is the cheat sheet experienced LLM PMs reach for before opening an IDE.

Table 67.3.1: 40.3.1 Mapping problem shapes to LLM capabilities (2026).
Problem shape Best-fit capability Failure mode to plan for Typical 2026 cost
Extract fields from messy documents Structured outputs with schema validation Silent field swaps; hallucinated values $0.001-0.01 per document
Answer questions from a private corpus RAG with grounded citations Retrieval misses; stale chunks $0.005-0.05 per query
Route or classify with explanations Few-shot classification + reasoning Edge cases that look like training examples $0.0005-0.005 per item
Draft long-form text from notes Drafter pattern with human-in-loop edit Wrong tone; fabricated facts $0.01-0.10 per draft
Execute multi-step business processes Agent with tools and checkpoints Tool errors; goal drift; partial execution $0.10-1.00 per task
Translate between data schemas Small model with strict JSON schema Schema violations; rare-type regressions $0.0001-0.001 per record
Pair-program inside an IDE FIM-trained code model with repo context Outdated API usage; broken refactors $10-40 per developer/month

The right column is the budget-shaping number. An extraction pipeline can support a $9/month consumer SaaS plan; an agentic workflow at a dollar per task cannot. Knowing this before you write code is what prevents the pattern Section 62.1's "budget that was never written down" example warned about: shipping a product whose unit economics quietly invalidate the business case.

67.3.3 One Capability Per MVP

The single most reliable correlation in early-stage LLM products is between "number of capabilities in the first release" and "did the project ship." Products that try to combine extraction, RAG, drafting, and agentic action in their v1 rarely make it past the prototype. Products that pick one capability, prove it, and then expand almost always do.

The reason is mechanical. Each capability has its own evaluation harness, its own failure modes, its own cost profile, and its own latency budget. Combining them does not add complexity linearly; it multiplies. A product that does extraction-then-RAG-then-drafting has not three failure modes; it has dozens of failure modes at the seams between capabilities, plus the cumulative latency, plus the cumulative cost. Most teams cannot reason about that combinatorial complexity until they have shipped at least one single-capability product first.

Warning: the "agent that does everything" trap

In 2024-2025 a class of demos appeared that promised "agents that handle your whole workflow end-to-end." Most never reached production. The pattern is consistent: a glossy demo for a single happy path, no eval harness, no cost ceiling, no documented failure handling. The teams that did ship agentic workflows in production did so by starting with extraction or RAG, getting it stable, and only then adding agent loops on top. Applied LLMs (Huyen, Bittner et al.) documents this pattern across a dozen interviewed teams. If your v1 plan involves multiple capabilities stacked, shrink it first.

67.3.4 The Output: A One-Paragraph Hypothesis

The deliverable from Chapter 67 is one paragraph. It fills in the following template, and it is short enough to print on a card: "We believe that [user persona] will pay [amount] to have an LLM do [one capability from the table above] on [input type] to produce [output type], and the riskiest assumption is [thing that, if false, kills the project]."

If you can fill in those blanks, you are ready for Chapter 62, which converts the hypothesis into a product spec with latency budgets, cost ceilings, quality thresholds, and the cross-functional contracts that hold the project together once engineering starts. If you cannot fill in the blanks, you are not ready to write code; the right response is to spend another week on Section 67.2's heuristics or Section 67.1's three-property check, not to start prototyping.

Tip: write the one-paragraph hypothesis before any technical work

The single biggest discipline-multiplier in LLM product work is to write the one-paragraph hypothesis on day zero and version-control it. When the project drifts six months from now (and it will), the original paragraph is the artifact that tells you whether the drift is intentional or accidental. Teams that skip this step end up six months in with no way to answer "is this still the same product we started building?" Save yourself the future argument and write the paragraph now.

Key takeaway
  • The bet-my-money test filters out 80% of brainstormed ideas via three sub-questions: pays, recoverable failure, defensible moat.
  • Different LLM capabilities have wildly different cost-quality-latency profiles; mis-mapping costs weeks of engineering.
  • One capability per MVP; combining capabilities multiplies failure modes rather than adding them.
  • The chapter deliverable is one paragraph that fills in user, amount, capability, input, output, and riskiest assumption.
  • Without that paragraph you are not ready to spec a product, let alone write code.
