LLM-Powered Robotics: Navigation, Planning, and Multi-Robot Coordination

Section 32.2

Section 32.1 introduced the VLA as a reactive policy: instruction in, motor tokens out, single horizon. Section 32.2 zooms out to the planner that sits above one or many VLAs. The questions at this layer are not "what joint angle do I emit next" but "what task should I attempt next", "is this room the right place to look for the cup", and "should robot A wait while robot B finishes". The 2022 lineage starts with SayCan; the 2025 frontier is multi-robot dispatchers running on small frontier LLMs that issue commands to fleets of cheaper VLAs.

This section walks through that lineage in roughly chronological order, then steps back to consider the cost versus reliability trade-off any production robotics team has to manage. We close on the sim-to-real gap and where ROS 2 fits into the 2026 stack.

32.2.1 SayCan: grounding LLM plans in robot affordances

SayCan (Google, 2022) is the canonical baseline. The insight: an LLM is excellent at decomposing "I spilled my drink, can you help" into ordered subtasks, but it has no idea what the robot can actually do. SayCan solves this by scoring each candidate next subtask by two probabilities multiplied together: p(task makes sense given the instruction), computed by an LLM, times p(robot can perform task here), computed by a separately trained affordance model that estimates feasibility from the camera image. The robot executes the highest-scoring step, observes, and replans. The framework is dated by 2026 standards (the affordance model is now usually a finetuned VLM, and replanning is incremental rather than per-step), but the factorization survives: what to do and can I do it are still separate computations.

SayCan is constrained decoding for robots

"Multiply the LM's distribution over candidate next-actions by an external scoring function" is exactly the constrained / logit-biased decoding pattern from Section 5.3. In text, the external scorer is a grammar, a regex, or a contrastive model; in SayCan, it is an affordance VLM. The product-of-distributions trick is the same. The Ahn et al. paper (Google, 2022, arXiv:2204.01691) makes this observation explicit: SayCan is a reranker on the LM's logits.

32.2.2 Code as Policies: the LLM writes a program, not a plan

Code as Policies (Google, 2023) replaced the discrete-step planner with a Python program generator. The LLM is prompted to emit code that calls a fixed API of robot primitives (pick(object), place(target), get_pose(object)) and Python control flow (for, if, list comprehensions). The benefit is composition: an LLM can chain primitives into novel control structures without retraining anything. The drawback is fragility: the LLM has to know exactly which primitives exist and what they return, and a single hallucinated function call halts execution. The 2026 successor pattern uses constrained decoding (the LLM can only emit tokens from a grammar that matches the API) plus tool-use protocols (Chapter 27) to make the API surface explicit.

Code-as-Policies is function-calling, period

Strip the robot-specific terminology and Code as Policies is just function-calling with the robot's skill library as the tool inventory (Section 27.1). The 2023 paper predates MCP and modern tool-use schemas, but the architectural pattern is unchanged: an LLM emits structured calls into a fixed set of primitives, an executor invokes them, results feed back into the next turn. Read Liang et al. (2023, arXiv:2209.07753) alongside Section 27.1 and the only delta is that the tools manipulate joints instead of HTTP endpoints.

# Code-as-Policies output for "stack the blocks by color"
blocks = detect_objects(filter="block")
colors = sorted(set(b.color for b in blocks))
for color in colors:
    same_color = [b for b in blocks if b.color == color]
    base = same_color[0].pose
    for b in same_color[1:]:
        pick(b)
        place(base + Vec(0, 0, 0.05))   # stack 5 cm above

32.2.3 VoxPoser: language as a spatial cost field

VoxPoser (Stanford, 2024) is the third lineage point and is structurally different. Instead of emitting symbolic plans or code, VoxPoser uses the LLM to write code that constructs 3D voxel cost maps: an "attractor" field around the cup the robot should approach, a "repeller" field around obstacles to avoid. A standard motion planner then chases the gradient of those fields. The trick is that the language grounding ("not too close to the stove") becomes a quantitative, dense, optimizable signal. VoxPoser composes naturally with VLAs: the VLA generates short-horizon motions, VoxPoser supplies the long-horizon cost shape.

Three ways to compile language to action

SayCan compiles language to a ranked list of discrete actions. Code as Policies compiles language to a Python program over primitives. VoxPoser compiles language to a spatial cost field. Every 2026 production planner is a hybrid of these three: the LLM emits a program (Code-as-Policies), each primitive in the program has an affordance check (SayCan), and continuous motion uses cost maps (VoxPoser). The lineage is not "old vs new"; it is "three complementary compilation targets".

Hierarchical planning is nested chain-of-thought

The dispatcher / VLA / low-level controller stack later in this section is a multi-rate hierarchical planner: high-level decomposition at 1 Hz (LLM), mid-level skill execution at 10 to 50 Hz (VLA), low-level control at 1 kHz (PID or MPC). That is hierarchical chain-of-thought from Section 14.2 made embodied: the LLM emits strategic directives, each directive triggers a finer-grained reasoning loop, the inner loop emits motor commands. The "scratchpad" of a reasoning model and the "directive" of a fleet dispatcher are the same primitive at different time scales.

32.2.4 Multi-robot coordination via a shared LLM dispatcher

The 2025 frontier is multi-robot coordination. The architectural pattern that scaled: one moderately powerful LLM (typically Claude Haiku 4.5 or Gemini Flash) acts as a fleet dispatcher; each robot runs a smaller, faster VLA locally. The dispatcher receives status updates from each robot (current task, battery, location, recent failures), issues new tasks, and resolves conflicts (robot A is in robot B's path, defer one). Covariant's warehouse deployments and Amazon's Sequoia and Sparrow fleets are the public reference deployments; the academic survey lineage runs through SMART-LLM (2024) and RoCo.

A dispatcher of robots is a multi-agent system

One LLM, many specialist VLA agents, status messages flowing back, task assignments flowing out. That is the multi-agent orchestration pattern from Section 28.1 with bodies instead of browsers. The supervisor / worker hierarchy, conflict resolution by replanning, and rate-limited communication are all carried over without modification. Read RoCo (arXiv:2310.10845) and SMART-LLM (arXiv:2402.04835) as embodied special cases of the patterns you already absorbed from Module 28.

32.2.5 ROS 2 integration: the messaging substrate

ROS 2 remains the dominant middleware for actually wiring all of this together. The 2026 production stack is roughly: a Python LLM-planner node publishes goal messages on a topic; a VLA node subscribes, executes, and publishes status; safety monitors run as separate nodes that can preempt motion. The ros2_llm packages provide canonical wrappers. The reason ROS 2 wins is unglamorous: it has the time-synchronized multi-process pub/sub, the dozens of supported sensors, and the safety-cert pathway that an LLM-only stack does not.

The cost vs reliability trade-off

Every step that calls an LLM costs latency (50 to 500 ms) and money (fractions of a cent each but they add up). A VLA running locally at 10 Hz issues 36000 control steps per hour. Calling an LLM at every step is economically and physically infeasible. The 2026 production pattern: LLM at the planning layer (~1 Hz), VLA at the action layer (10 to 50 Hz), low-level controller (~1 kHz). Mixing layers is the most common cost overrun in robotics deployments. Cache aggressively; replan only when the world surprises you.

Edge robot deployment IS inference optimization

The latency / throughput / VRAM trade-offs that define what you can run on a Jetson Orin or other onboard accelerator are the same ones from Section 10.1 (quantization), Section 10.3 (KV cache), and the rest of Module 10. A VLA quantized to INT8 with a paged KV cache is the same engineering as a server-side chat model under the same techniques. The robot context only changes the SLO numbers: a 100 ms latency budget instead of a 500 ms one, a 12 GB VRAM ceiling instead of an 80 GB one, but the levers (KV reuse, prefill batching, speculative decoding, weight-quantized GEMMs) are unchanged.

32.2.7 Sim-to-real: the gap that has not closed

Despite five years of work, the sim-to-real gap is real. Policies trained in Isaac Sim or Genesis still lose 15 to 30 percentage points of success when transferred to real hardware without further finetuning. The 2026 frontier mitigations are domain randomization (vary visual textures, lighting, friction during sim training), real-to-sim grounding (use Gaussian splats of the actual factory floor as the sim background, covered in section 32.3), and world-model rollouts trained from real video (section 32.4). None of these are a silver bullet; the production reality is that you collect real-world demonstrations after sim pretraining and you finetune.
