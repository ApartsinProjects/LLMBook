Platforms

Section 41.1

The "platforms" of Part V are the managed and self-hosted vector databases. The vector database is where the embeddings live; everything else in a RAG system orbits around it.

25.1.1 Managed vector databases

Three 2024-25 entrants reshape the managed-DB landscape worth flagging before the established list. Turbopuffer is an object-storage-native vector DB (vectors and metadata live in S3/R2; query nodes are stateless) and the cheapest-at-scale option of 2025 for read-heavy RAG. Chroma Cloud (2024) is the managed version of ChromaDB, relevant for teams who started on the local prototype and want to graduate without changing the API. Vespa (Yahoo open source) is underrated and powers some of the largest production RAG systems; pick it when you want a search engine that happens to do vector search rather than a vector store retrofitted with text.

For "I already run X" readers: Couchbase Vector and Redis 8 vector search both shipped in 2024; Elasticsearch ELSER + dense vector (Elasticsearch 8.x) is the right path if Elastic is already in your stack.

  • Pinecone (Pinecone, 2019) is the longest-running managed vector database and the one most enterprise RAG teams default to. Its objective is to remove all infrastructure decisions from vector search so you can stand up a production retrieval layer in an afternoon, which matters when your bottleneck is shipping a product rather than tuning a database. The core concept is "namespaces" (logical sub-indexes inside one index) for multi-tenant SaaS plus first-class hybrid search that fuses dense and sparse (BM25-like) scores. Pick Pinecone when ops convenience outweighs cost; avoid when your scale exceeds tens of millions of vectors and per-namespace pricing becomes painful.
  • Weaviate Cloud (Weaviate, 2019) is the managed version of the open-source Weaviate vector database, distinguished by a built-in module system that handles embedding generation, multi-modal storage, and generative-search loops inside the database. Its objective is to make the entire RAG pipeline (chunk, embed, store, search, generate) configurable in one place, which matters when you want the database to own embedding consistency rather than relying on application code. The core concept is a typed schema with classes and properties (more SQL-shaped than Pinecone) plus pluggable vectorizer and reader modules. Pick it when you want an opinionated end-to-end RAG store; pick Pinecone when you just need raw vector search.
  • Qdrant Cloud (Qdrant, 2021) is the managed offering for the Rust-based Qdrant engine, designed around HNSW-with-payload filtering as a first-class operation. Its objective is sub-millisecond p99 latency under heavy filtered-search load, which matters for autocomplete-style or real-time retrieval where users notice 50 ms of latency. The core concept is "payload-indexed filters" that let you combine vector similarity with structured predicates (date ranges, tenant IDs) without falling off the HNSW happy path. Pick Qdrant when latency is the binding constraint or when you have heavy metadata filtering.
  • MongoDB Atlas Vector Search (MongoDB, 2023) bolts vector indexing onto Atlas, letting your existing document collections grow a $vectorSearch stage in the aggregation pipeline. Its objective is to eliminate the second database your application would otherwise need, which matters when your team already runs Mongo and operational simplicity outweighs raw vector performance. The core concept is that vectors live alongside their source documents; no second consistency boundary. Pick when "we already run Atlas" is true; for greenfield RAG, a specialist DB is usually better.
  • Azure AI Search (Microsoft, 2014 as Azure Search; vector in 2023) is Microsoft's full-text search engine retrofitted with vector and hybrid retrieval. Its objective is to provide the same primitive as Pinecone with Azure-native auth, networking, and compliance, which matters when your enterprise security review will not approve a third-party SaaS. Pick it inside the Azure ecosystem; avoid outside it.

25.1.2 Self-hosted and embedded

  • Chroma (Chroma, 2023) is the embedded, Python-first vector database that became the default for RAG prototypes and tutorial code. Its objective is "pip install chromadb and write five lines of code", which matters when you want to evaluate whether RAG works at all before paying for managed infrastructure. The core concept is a single-process DuckDB-backed store with a one-method add/query API; persistence to disk is optional. Pick Chroma for prototypes, Jupyter notebooks, and small CLI tools; avoid in production where multi-process access or large indexes are needed.
  • FAISS (Meta FAIR, 2017) is the C++ ANN search library that essentially every other vector DB uses (or studied) underneath. Its objective is to provide the most efficient possible implementation of IVF, HNSW, PQ, and OPQ indexes for billion-scale similarity search, which matters when you need maximum recall-per-dollar at search time. The core concept is a low-level Index abstraction with composable quantizers and a Python wrapper; it is a library, not a database (no networking, no metadata, no persistence layer beyond write_index). Pick FAISS when you are willing to write a thin wrapper for ultimate control; avoid when you need a DB rather than a kernel.
  • pgvector (Andrew Kane, 2021) is the Postgres extension that adds a vector column type and ivfflat / HNSW indexes. Its objective is to keep your retrieval store inside the database you already run for everything else, which matters when transactional consistency with the application data is more valuable than peak vector performance. The core concept is a normal Postgres column whose ORDER BY uses cosine, L2, or inner-product distance; the DB optimizer chooses an HNSW or sequential scan as appropriate. Pick pgvector whenever "I already run Postgres" is true and you have under ~10M vectors; above that, specialist DBs scale better.
  • Milvus and Zilliz Cloud (Zilliz, 2019 / 2022) together form the distributed open-source vector database (Milvus) and its managed sibling (Zilliz Cloud), engineered explicitly for billion-vector and multi-tenant SaaS scale. Their objective is to scale horizontally across nodes with separate compute and storage tiers, which matters when no single machine has enough RAM for your index. The core concept is a cloud-native architecture (proxy, coordinator, query nodes, data nodes) that maps onto Kubernetes; expect the operational complexity to match. Pick Milvus / Zilliz when scale is the binding constraint; for under 100M vectors, simpler stacks are easier.
  • LanceDB (LanceDB, 2023) is a columnar embedded vector database built on top of the Lance file format (an Arrow-compatible columnar store with versioning). Its objective is to give you the convenience of Chroma with the analytics-friendly columnar layout you would normally need a separate data warehouse for, which matters when your application does mixed vector + analytical queries (find similar docs, then aggregate by date). The core concept is "vectors as just another Arrow column" with zero-copy reads. Pick LanceDB when you want both ANN and OLAP-style queries on the same data; for pure vector search, Chroma or Qdrant are more focused.

25.1.4 Choosing

For prototypes: Chroma. For small-to-medium production with existing Postgres: pgvector. For latency-sensitive search: Qdrant. For ops convenience: Pinecone. For billion-vector or multi-tenant SaaS: Milvus/Zilliz. The choice rarely matters at fewer than 1M vectors; it matters a lot at more than 100M.

Index type matters more than DB choice

All major vector DBs ship HNSW, IVF, and quantized indexes. The specific quantization variants you should know in 2026 are Product Quantization (PQ), scalar quantization (1-bit through 8-bit), binary quantization, and Matryoshka-style truncation (chop the embedding dim before storing). The choice of index type and parameters usually determines recall and latency more than the choice of DB engine.

Case study: Anthropic Contextual Retrieval (Sep 2024)

Anthropic's "Contextual Retrieval" engineering post (Sep 2024) is the canonical 2024-25 production-RAG technique: prepend a short (50-100 token) AI-generated document-level context to each chunk before embedding, so the chunk's embedding captures both local and document-level meaning. Combined with BM25 + dense hybrid retrieval and Cohere Rerank, the technique cut retrieval failure rates by ~67% on Anthropic's internal eval. It is the strongest single procedural change in production RAG since 2023.

GraphRAG and knowledge-graph hybrids became serious in 2024-25

Microsoft's GraphRAG (2024) and the broader knowledge-graph + RAG hybrid line became significant in 2024-25, particularly for multi-hop reasoning over long documents where pure vector retrieval misses cross-chunk relationships. Worth considering when "answer requires synthesizing across many chunks" is your failure mode.
