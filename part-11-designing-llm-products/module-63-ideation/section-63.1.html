Ideation: Finding LLM-Worthy Problems

Section 63.1

"The model is the easy part. The hard part is finding a problem worth solving with it, and then proving that the solution actually saves someone time, money, or grief."

A Pragmatic Compass, Problem-Hunting AI Agent
Big Picture

Ideation for LLM products is the practice of finding problems where a language model is the cheapest, fastest, or only viable solution. The frontier shifts every quarter: tasks impossible in 2022 became one-line API calls by 2024, and what felt like sorcery in 2024 is now table stakes. The danger is symmetrical. Build the wrong thing and you produce an expensive demo that nobody uses; refuse to build at all and a competitor ships a product that quietly eats your market. This section gives you a structured way to separate problems that genuinely benefit from an LLM from problems that look LLM-shaped but are better solved by a spreadsheet, a SQL query, or a phone call.

Prerequisites

This section assumes familiarity with the LLM capability landscape from Section 8.1 and the basics of LLM API patterns from Chapter 13. Readers who have skimmed Chapter 26 on agentic systems will recognize many of the capability buckets discussed below.

58.1.1 What Kinds of Problems LLMs Solve Well

Before generating ideas, calibrate against what the technology is actually good at. A language model is, at its core, a probabilistic function that maps text (and increasingly images, audio, and structured data) to more text. Wrap a few prompts around it, give it tools and memory, and it becomes a reasoning surface that can attack a wide range of tasks. But the surface has shape. Some regions are flat and reliable; others are jagged.

The following capabilities crossed the production threshold by 2026, meaning teams routinely ship them in revenue-bearing products without heroic engineering:

  • Unstructured-to-structured transformation. Extracting fields from messy documents, parsing emails into tickets, turning meeting transcripts into action items. The classic structured outputs use case. Margins are high because the alternative is a human reading the document.
  • Summarization and synthesis. Condensing long inputs into shorter, useful artifacts: research briefs, ticket triage notes, customer call summaries. Quality varies by domain, but the failure mode (a summary that misses a nuance) is usually recoverable.
  • Drafting and rewriting. First drafts of emails, marketing copy, code, legal templates, support replies. The model gives a 70% draft in seconds; a human polishes the last 30%. The economics work because polishing is faster than starting from a blank page.
  • Classification and routing with context. Sentiment, intent, priority, topic, escalation level. Traditional ML can do this, but LLMs win when you have few labels, many edge cases, and a need for explanations.
  • Retrieval-augmented question answering. Answering questions grounded in a corpus you control (docs, wikis, codebases) using the RAG patterns from Chapter 23. The single most common pattern for internal tools.
  • Multi-step agentic workflows. Booking, scheduling, web research, code modifications, customer onboarding flows. Reliability is still uneven, but the surface area expands every month. See the agent patterns in Chapter 26.
  • Conversational interfaces over data. "Ask your database in English" or "ask your codebase." When the underlying data is well-structured, the model becomes a translation layer between natural language and the system that actually answers.
Key Insight

LLM-worthy problems share three structural properties. First, the input is unstructured or semi-structured text that a human would normally read. Second, the output is also language-shaped: a summary, classification, draft, or decision. Third, the value of getting it right is much higher than the cost of an occasional wrong answer (or you have a cheap way to catch the wrong ones). When all three hold, an LLM is usually the dominant solution. When one is missing, ask harder questions.

58.1.2 What Kinds of Problems LLMs Still Do Poorly

It is just as important to know the dead zones. The following problem shapes remain difficult enough in 2026 that you should treat them as red flags during ideation, not casual sprints:

  • Tasks that demand provable correctness. Tax calculations, payroll, medication dosing, safety-critical control systems. Even a 99.9% accurate LLM is a 1-in-1000 failure rate, which is unacceptable when the failure is "wrong drug administered." Use traditional software with the LLM as a side advisor, not the system of record.
  • Long-horizon planning with no human checkpoint. Agents still drift over multi-day horizons. The compounding-error math from Section 66.1 is unforgiving: ten 95%-accurate steps yields 60% end-to-end success. If your problem requires a 50-step plan with no checkpoint, the model cannot yet do it reliably.
  • Real-time, low-latency loops. Sub-100ms response budgets, high-frequency trading, embedded control. Frontier models cost hundreds of milliseconds per call before any reasoning chain. A specialised model or deterministic algorithm usually wins.
  • Problems where data is the constraint, not reasoning. If the answer requires information no one has written down (proprietary lab results, internal pricing, tomorrow's weather), the LLM cannot manufacture it. Build the data pipeline first.
  • Tasks that are already cheap and reliable. Spell-checking, currency conversion, lookup tables, regex matching. Reaching for an LLM to do work that a 50-line Python script handles is the most common rookie mistake.
Warning: The "LLM as Hammer" Trap

Once a team has built one successful LLM feature, every subsequent problem starts to look like a nail. Resist this. Before you write a prompt, ask whether a SQL query, a rule-based classifier, a regular expression, or a phone call would solve the problem cheaper and more reliably. The cheapest LLM call is the one you never made. The tail-latency math from distributed systems research applies in spades: at scale, every variable-latency call you avoid is money in the bank.

58.1.3 Problem-Discovery Heuristics

Knowing the shape of LLM-worthy problems is necessary but not sufficient. You still have to find them. The following heuristics repeatedly turn up real problems in real organizations.

Heuristic 1: Follow the "I wish I had an intern" complaint. Walk around your company (or your customers') and listen for "I just wish I had someone who could…" followed by something tedious, language-shaped, and not safety-critical. "Read these 200 emails and pull out the ones that mention contract renewal." The speaker has already done the willingness-to-pay calculation: an intern would cost real money.

Heuristic 2: Look for the "manual handoff" in the workflow. Every business process has a moment where a human reads something written by another human and decides what to do next: route the ticket, escalate the complaint, classify the lead. These handoffs are bottlenecks, variable, and expensive. They are exactly the shape an LLM eats for breakfast.

Heuristic 3: Find the moments where users abandon. Wherever users quit mid-flow, ask why. Often the answer is "the task got too complicated to complete unaided." A coding tutorial site loses 40% of users at the "set up a Python environment" step; an LLM assistant that walks them through it could recover much of that drop. The "do things that don't scale" tradition applies: solve one user's abandonment manually, then automate.

Heuristic 4: Watch for "the language barrier between two systems." Whenever a process translates between two formats, vocabularies, or schemas, a language model can be the translator. "Take this customer email and turn it into a Jira ticket with the right labels." Schema mismatch is the workhorse of B2B integrations, and LLMs are now the cheapest bridge.

Heuristic 5: Read your own customer support tickets. If the same five questions appear every week and a human could answer in under three minutes, you have a textbook RAG opportunity. Public studies show 30 to 50 percent of mature SaaS support tickets fall into this pattern.

Real-World Scenario: The Insurance Adjuster's Inbox

Who: A product manager at a mid-sized property and casualty insurer.

Situation: Claims adjusters were spending 45 minutes per claim reading photos, repair estimates, and policy documents before deciding how to process it. With 800 adjusters and 30 claims per day each, this was 18,000 hours per day of pure reading.

Discovery: The PM shadowed three adjusters for a week. The most common phrase she heard was "I just need someone to tell me what's in this document so I can decide." Classic "I wish I had an intern" signal; the handoff between unstructured PDF and structured claim form was the bottleneck.

Result: A scoped prototype using Claude's document understanding and a small validation prompt reduced the average reading time from 45 minutes to 6 minutes per claim. The adjuster still made the decision, but they no longer had to manually extract the facts that fed it.

Lesson: The best LLM ideas come from spending an hour watching someone do the job, not from a brainstorming session in a conference room.

58.1.4 The "Bet My Own Money" Test

Brainstormed ideas are cheap; funded projects are expensive. Between the two sits a single sharp test that filters out 80% of the garbage: would you bet your own money on this? Not your employer's money, your own.

The test is a stand-in for three uncomfortable questions you have to answer honestly:

  1. Would the user actually pay for this? Not "would they say nice things in a survey," but "would they hand over a credit card?" If the user already has the budget for an intern, a software license, or a consultant doing this work, willingness to pay is established. If not, you have a marketing problem on top of an engineering one.
  2. Can I describe the failure mode in one sentence, and is the failure recoverable? "The model writes a wrong summary and the analyst notices in 10 seconds" is recoverable. "The model approves a fraudulent transaction and the bank loses \$50k" is not. If you cannot describe the failure, you have not thought about it hard enough.
  3. Is there a moat besides the prompt? A 50-line OpenAI API wrapper is not a defensible product in 2026. The moat has to come from proprietary data, distribution, workflow integration, regulatory compliance, brand trust, or switching costs. If the answer to "what stops a competitor from rebuilding this in a weekend" is silence, go in with eyes open about the timeline before commodification.
Tip: The Willingness-to-Pay Sniff Test

Before investing engineering time, run a paid-pilot conversation with three real users. Ask: "If we built this, would you pay $X per month for it?" Then halve X and ask again. If they hedge at half the price, you are not on a real problem; you are on a wishful one. The Startup School library has dozens of variations on this test, but the core mechanic is the same: get someone to commit to money before you commit to code.

58.1.5 Mapping Problems to LLM Capabilities

Once a candidate problem survives the bet-my-money test, the next step is mapping it onto the LLM capability that will actually solve it. Different capabilities have different cost curves, latency profiles, and failure modes. Mis-mapping is what turns a six-week MVP into a six-month engineering swamp. The following table covers the patterns that show up most often in real product work.

Table 58.1.1: Mapping Problem Shapes to LLM Capabilities (as of 2026).
Problem shape Best-fit LLM capability Failure mode to plan for Where to read more
Extract fields from messy documents Structured outputs with schema validation Silent field swaps; hallucinated values Section 14.1
Answer questions from a private corpus RAG with grounded citations Retrieval misses; stale chunks Chapter 23
Route or classify with explanations Few-shot classification + reasoning Edge cases that look like training examples Section 14.1
Draft long-form text from notes Drafter pattern with human-in-loop edit Wrong tone; fabricated facts Section 66.2
Execute multi-step business processes Agent with tools and checkpoints Tool errors; goal drift; partial execution Chapter 26
Translate between data schemas Small model with strict JSON schema Schema violations; rare-type regressions Section 13.1
Pair-program inside an IDE FIM-trained code model with repo context Outdated API usage; broken refactors Section 64.2

The right column points to the chapter that turns the choice into concrete code; the left column is what to write on the whiteboard before opening an IDE. Skipping this map is one of the most consistent reasons LLM products run over budget.

Key Insight

Pick one capability per MVP. The fastest path to a working product is to scope it down to a single LLM capability (extraction, RAG, drafting, routing, or agentic action) and build the rest of the system around that one capability. Products that try to combine all five in their first release rarely ship. Products that pick one, prove it, and then expand almost always do.

58.1.6 A 30-Minute Ideation Workshop

Putting it all together: the following workshop format has produced shippable LLM product ideas in a single afternoon. It is short on purpose. Long brainstorms produce long lists of mediocre ideas; tight constraints force ruthless prioritization.

  1. Five minutes: Collect "I wish I had an intern" quotes. Each participant writes three real quotes they have heard (or said) in the past month.
  2. Five minutes: Cluster the quotes by capability, using the table from Section 63.1.5. Quotes that do not fit any capability get a question mark.
  3. Ten minutes: Run the bet-my-money test on the top three clusters. For each, the group answers willingness-to-pay, failure recovery, and moat in one sentence. Anything failing any of the three is set aside.
  4. Five minutes: Sketch the smallest possible MVP for the winner. One LLM call, one input, one output, one user. Do not let scope creep in.
  5. Five minutes: Identify the riskiest assumption. The one thing that, if false, would kill the project.

The output is a single paragraph: "We believe that [user] will pay [amount] to have an LLM do [capability] on [input] to produce [output], and the riskiest assumption is [thing]." If you cannot fill in those blanks, you are not ready to write code.
