66.1.1 AI-native code editors and assistants

  • Cursor (Anysphere, 2023) is the VS Code fork with first-class LLM integration: chat in the sidebar, agent that edits across files, and tab-autocomplete tuned for code. Its objective is to be the AI-first version of the editor most developers already use, which matters because plugin-based AI integrations (Copilot in stock VS Code) lag native experiences in latency and quality. The core concept is full editor agency: the AI can read your whole codebase, run terminal commands, and propose multi-file diffs. Pick Cursor as the production-default AI editor in 2026.
  • Claude Code (Anthropic, 2024) is the terminal-based agentic coding tool powered by Claude, designed for developers who prefer a CLI workflow. Its objective is to provide an agent that operates on real codebases with read, write, edit, and shell access from your terminal, which matters when you want IDE-equivalent coding agency without the IDE. The core concept is a long-running agent that maintains context across many tool calls in a single session. Pick Claude Code for terminal-centric workflows or for non-IDE editing tasks.
  • GitHub Copilot (GitHub/Microsoft, 2021) is the original AI coding assistant, now multi-model (you can pick GPT-5, Claude Sonnet, or others as the backend). Its objective is to be the most ubiquitous IDE-integrated AI assistant via tight VS Code, JetBrains, and GitHub.com integration, which matters for enterprises with Microsoft procurement. Pick Copilot when your team is already on the Microsoft stack and you want one-vendor billing; for cutting-edge features, Cursor and Claude Code typically lead.
  • Cline (formerly Claude Dev, 2024) is the open-source VS Code agent extension, BYO API key. Its objective is to provide Cursor-shaped functionality as an open-source extension you can audit and self-modify, which matters for security-conscious teams. Pick Cline for transparent, hackable agent integration in stock VS Code.
  • Aider (Paul Gauthier, 2023) is the open-source terminal-based pair programmer. Its objective is to provide AI-assisted git-aware editing from the terminal with no GUI, which matters for headless development and remote-server workflows. The core concept is per-commit-style edits: Aider proposes diffs, you accept or reject, and changes land as well-formed git commits. Pick Aider for terminal git-native workflows.
  • Windsurf (Codeium, 2024) is Codeium's AI-first IDE, a separate editor (not a VS Code fork) competing with Cursor. Its objective is to be a more ambitious AI editor with explicit Flow Awareness (the agent watches your typing patterns) and Cascade (a long-horizon multi-file agent). Pick Windsurf when you want a Cursor competitor with a different agent design; both are credible picks in 2026.
  • Zed AI (Zed Industries, 2024) is the Rust-based editor with native LLM integration, the spiritual successor to Atom from its original creators. Its objective is to provide a blazing-fast editor that does not feel like a re-skin of Chrome, which matters for developers who find Electron editors sluggish. Pick Zed AI when editor performance matters and you want first-class collaborative editing.
  • Replit Agent (Replit, 2024) is the in-browser coding-agent-in-IDE, building entire apps from natural-language descriptions. Its objective is to make in-browser app development end-to-end (idea, generation, deployment) without leaving the browser, which matters for educational settings and rapid prototyping. Pick Replit Agent for in-browser prototyping and teaching; for serious production code, desktop editors are still preferred.

Deployment Patterns

What this section is

The reference for rolling out a new model version, a new prompt, or a new agent without breaking production. Four patterns (canary, blue-green, shadow, A/B test) plus feature flags for prompts together cover every safe-rollout scenario in an LLM stack. We walk each pattern, the tools that ship it (GitOps with ArgoCD, Flagger, LaunchDarkly, vendor-native A/B in LangSmith and Langfuse), and the decision rule for picking among them.

The conceptual treatment of production engineering and rollout strategy lives in Chapter 45 (Production Engineering). This section is the operational counterpart: which Kubernetes resource you actually apply, which flag-evaluation latency you should worry about, and how the patterns combine with the monitoring loop from Section 48.2 (Libraries & Frameworks). Cross-references to Section 12.2 (Libraries & Frameworks) for the underlying serving infrastructure and Section 62.7 (Docker Fundamentals: Images, Containers, and Volumes) for the image-promotion mechanics are flagged inline.

O.3.1 The Four Rollout Patterns

Each pattern answers a different question about risk and observability. Picking the right one is more about what you can measure before users see the new version than about the deployment mechanics themselves.

Canary: route a small fraction of live traffic (typically 1%, then 5%, then 25%, then 100%) to the new version while keeping the old version serving the rest. You compare error rates, latency, and eval-in-prod quality scores between the two cohorts. Canary is the right default when you trust your monitoring to detect a regression within the canary window. It is cheap, reversible, and produces a clean A/B comparison for the metrics you instrumented.

Blue-green: stand up the new version (green) in parallel to the current production (blue), point your load balancer at green in a single cutover, and keep blue warm for instant rollback. There is no traffic-split phase; the comparison is between empty and full traffic. Blue-green wins when you cannot tolerate a mixed-version cohort (e.g., a multi-turn agent where the same user must not hit different versions across turns) or when the new version requires schema changes that cannot coexist with the old one.

Shadow mode: mirror live requests to the new version but discard its responses; users see the old version's output. The new version sees real traffic and you can measure its behavior offline (latency, response distribution, eval-in-prod quality) without exposing users to its mistakes. Shadow is the right choice for high-stakes changes (a new base model, a major prompt overhaul) where you want production-load characterization before any user impact.

A/B test: deliberately split traffic between two versions and measure a user-level outcome (CSAT, task completion, downstream conversion) with statistical power. Unlike canary, A/B is not about catching regressions, it is about deciding which version is better on a metric that takes days or weeks to accumulate signal.

Key Insight

Canary and A/B look similar from 30,000 feet but answer different questions. Canary asks "is the new version safe to roll out?" and runs for hours; A/B asks "which version maximizes outcome X?" and runs for days to weeks. Conflating them produces noisy results: a 24-hour canary cannot detect a CSAT lift, and a two-week A/B can be sabotaged by a bug that should have been caught in canary on day one.

O.3.2 Feature Flags for Prompts and Model Versions

The classic feature-flag pattern (Stripe, LaunchDarkly, OpenFeature) becomes more useful in LLM stacks because the unit of change is often not code but text: a prompt template, a few-shot example list, a model identifier, a temperature value. Treating these as flags lets you change behavior in seconds without a deploy, and lets you scope a change to a user segment ("internal employees only", "10% of free-tier users", "all enterprise on plan tier 3").

LaunchDarkly and OpenFeature are the vendor and OSS standards for general feature flags; both work for prompts but lack LLM-aware tooling. Langfuse prompt management and LangSmith's prompt registry are LLM-native: they version prompts as first-class artifacts, support A/B variant labels per prompt, and emit usage telemetry tied to the prompt version so you can correlate a quality dip to a specific edit. Helicone added prompt experiments in 2024 with similar semantics scoped to its proxy.

from langfuse import Langfuse

lf = Langfuse()
# Prompt registered with two variants; Langfuse routes by user_id hash
prompt = lf.get_prompt(
    name="refund-policy-summarizer",
    label="production",  # or "canary", "experiment-a", etc.
    cache_ttl_seconds=300,
)
messages = prompt.compile(policy_text=POLICY, user_question=q)
# Emits a span linked to the exact prompt version used
response = openai_client.chat.completions.create(
    model="gpt-4o-2024-11-20",
    messages=messages,
)

O.3.3 GitOps and Progressive Delivery on Kubernetes

For self-hosted inference (vLLM, TGI, Ollama, custom servers from vLLM & Inference Servers) the standard 2024-2026 stack is GitOps with progressive delivery: ArgoCD reconciles Kubernetes manifests from a Git repository, and Flagger drives the canary or blue-green progression with automated metric checks. The model artifact is a container image (built per Section 62.7 (Docker Fundamentals: Images, Containers, and Volumes)); the rollout is a Kubernetes Deployment with a Flagger Canary resource that defines the traffic-shift schedule and the success thresholds.

A minimal Flagger canary for a vLLM deployment looks like this:

apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: llm-inference
spec:
  targetRef: {apiVersion: apps/v1, kind: Deployment, name: vllm-server}
  service:
    port: 8000
  analysis:
    interval: 1m
    threshold: 5         # how many failed checks before rollback
    maxWeight: 50        # peak canary share before promotion
    stepWeight: 5        # +5% traffic per interval
    metrics:
      - name: request-success-rate
        thresholdRange: {min: 99}
        interval: 1m
      - name: request-duration-p99
        thresholdRange: {max: 2000}  # ms
        interval: 1m
      - name: faithfulness-score      # custom Prometheus metric from Ragas
        thresholdRange: {min: 0.85}
        interval: 5m
Code Fragment n.3.2: A minimal Flagger canary for a vLLM deployment looks like this:.

The third metric, faithfulness-score, is the LLM-specific addition: a Prometheus exporter scrapes the Ragas judge from Section 48.2 (Libraries & Frameworks) and Flagger refuses to promote if quality dips. This composition is what closes the loop between drift detection and deployment automation.

The patterns compose. SLOs, Alerting, and FinOps

What this section is

The reference for the two operational disciplines that decide whether your LLM system is in good standing with both users and the finance team: SLOs and alerting for reliability, FinOps for cost. The two interact directly because almost every LLM cost optimization (prompt caching, batch APIs, lower-cost models) is also a latency intervention, and most reliability problems (retries, timeouts, fallback chains) directly drive cost.

The conceptual treatment of scaling economics and post-launch operations lives in Chapter 71 (Scaling Economics) and Chapter 68 (Post-Launch Monitoring). This section is the practitioner reference: which SLOs to define for LLM endpoints, how to wire alerts to PagerDuty or Opsgenie without paging on noise, and which three cost-attribution strategies cover the bulk of the FinOps work. The opening case study is the \$12,000 fintech bill from Appendix G War Story 5; the operational fix touches every concept in this section.

O.5.1 SLOs for LLM Endpoints

A Service Level Objective (SLO) is a target on a Service Level Indicator (SLI) measured over a window. For a stateless REST service the classical SLIs are availability (success-rate), latency (p99), and throughput; for an LLM endpoint you add LLM-specific SLIs that the classical set misses.

Availability: percentage of requests that return a successful response within the timeout. For LLM systems the timeout itself is a design choice (a 30s timeout for a chat completion is reasonable; a 30s timeout for a long-form generation is not). Target a 99.5% to 99.9% monthly SLO depending on user-facing criticality.

Latency, split: separate time-to-first-token (TTFT) from total response time. TTFT is what the user perceives as "the system is alive"; total time is what the user perceives as "the system is done". Set independent SLOs (TTFT p99 < 1s, total p99 < 30s) so a slow long-tail does not hide a TTFT regression. Inter-token latency p99 is a third useful SLI for streaming UIs.

Quality SLO (the LLM-specific addition): hallucination rate, faithfulness score, or refusal rate measured by eval-in-prod (Section 48.2 (Libraries & Frameworks)). A typical RAG SLO is "Ragas faithfulness p50 >= 0.85, p10 >= 0.70 over a 7-day window". Quality SLOs differ from availability SLOs in that you cannot fix them with a retry; the fix is a model, prompt, or retrieval change.

Cost SLO: per-request or per-user-session cost target. Without a cost SLO, the runaway-bill scenario (War Story 5) is a tail risk that hits you once and is then fixed reactively. With a cost SLO, an alert fires the moment per-session cost crosses a threshold and the kill-switch (P12 pattern from Chapter 45) trips automatically.

Key Insight

Quality and cost are SLIs in their own right for LLM systems, not derived consequences of availability and latency. Treating them as first-class with explicit SLOs is the single biggest operational maturity step beyond classical SRE practice; teams that skip this step end up paging on availability while quality silently degrades or while the bill triples.

O.5.2 Alerting, Error Budgets, and On-Call Wiring

An SLO without an alert is decoration. The standard pattern is to convert the SLO into an error budget (the complement: 0.1% downtime allowance for a 99.9% SLO) and alert on the rate at which the budget is being burned. Google's SRE workbook documents the multi-window, multi-burn-rate alerting policy that is now standard. The short form: a fast alert (5-minute window) catches acute outages; a slow alert (hour or day window) catches gradual degradation.

Wire alerts to PagerDuty or Opsgenie via the Prometheus Alertmanager (for self-hosted stacks) or directly from your observability backend (Datadog, Honeycomb, Grafana). The router rules matter: route LLM-specific alerts (quality, cost) to the ML on-call rotation, not the infra rotation, because the playbooks differ. A latency alert is fixed by adding capacity or rolling back a deploy; a quality alert is fixed by rolling back a prompt or model version, which is a different runbook and a different decision authority.

# Prometheus alerting rule: cost SLO with burn-rate alert
groups:
  - name: llm-cost-slo
    rules:
      - alert: PerSessionCostBurnFast
        expr: |
          (rate(llm_session_cost_usd_sum[5m])
           / rate(llm_session_cost_usd_count[5m])) > 0.50
        for: 2m
        labels: {severity: page, team: ml-platform}
        annotations:
          summary: "Avg per-session cost > $0.50 (target < $0.10)"
          runbook: "https://runbooks.company.com/llm/cost-spike"
      - alert: HallucinationRateBurn
        expr: |
          avg_over_time(ragas_faithfulness_p10[1h]) < 0.70
        for: 15m
        labels: {severity: page, team: ml-platform}
        annotations:
          summary: "Faithfulness p10 below 0.70 over 1h (quality SLO breach)"
Code Fragment n.5.1: Wire alerts to PagerDuty or Opsgenie via the Prometheus Alertmanager (for self-hosted stacks) or directly from your observability backend (Datadog, Honeycomb, Grafana).

O.5.3 FinOps: Per-Request Cost Attribution

The FinOps equation has three terms: vendor token (or self-host compute) cost, proxy and gateway cost, downstream cost (storage, network, eval-in-prod judges). The unit-economics question is the marginal cost of one user session, which requires emitting both input and output token counts on every span. The OpenLLMetry semantic conventions (Section 48.11) define gen_ai.usage.input_tokens and gen_ai.usage.output_tokens as standard attributes. Multiplying by per-model rate cards (which differ by 10x+ across models) gives per-span cost; aggregating by user_id, session_id, or feature flag gives the per-segment view. Helicone, Langfuse, and Phoenix ship this dashboard out of the box; rolling your own is one Prometheus exporter consuming the trace stream.

O.5.4 The 2024-2026 Cost Optimization Toolkit

Three vendor-side mechanisms cover most LLM cost optimization. Prompt caching (OpenAI, Oct 2024; Anthropic, Aug 2024; Gemini) charges ~10% of the normal input rate for cached tokens. For a RAG app where 90% of every prompt is shared context, this is a 5-10x reduction with no quality change. Batch APIs (OpenAI Batch, Anthropic Message Batches) charge ~50% with a 24-hour SLA, ideal for offline eval and content pipelines. Model routing sends easy queries to a cheaper tier (gpt-4o-mini, claude-haiku-4-5) and escalates only the hard ones; LiteLLM and Not Diamond are the 2024 entrants. For self-hosted serving (see vLLM Deep Dive) the levers are GPU utilization (idle vs busy: same dollars/hour), quantization (FP8 or INT4 weights), and continuous batching (vLLM's PagedAttention, TGI). A GPU at 50% utilization is a 2x cost overage compared to a properly batched one.

Postmortem: The \$12,000 Fintech Bill

The full case study is War Story 5 in Appendix G. The chain of failures: a buggy release produced 429 rate-limit errors at 5% of requests; the retry layer multiplied each failure by 7; the retry resubmitted the full 6K-token conversation history every time; no prompt caching was enabled; no cost SLO existed and no per-session cost alert fired. The \$12K bill arrived in 14 hours, vs an expected \$400. The remediation touched every section in this appendix: prompt caching for the shared prefix (50% input savings), jittered exponential retry with hard cap (P7 pattern), per-request cost attribution emitted on every span (Section 48.11), a per-session cost SLO with a fast-burn alert and an automatic kill switch (this section). The lesson is that no single fix would have prevented it; the production-engineering discipline is what would have.

Key Takeaway
  • Define four SLI families for LLM endpoints: availability, latency (split TTFT from total), quality (faithfulness, hallucination rate), and cost (per-request or per-session). Quality and cost are first-class, not afterthoughts.
  • Use multi-window multi-burn-rate alerts wired to PagerDuty or Opsgenie; route LLM-specific alerts (quality, cost) to the ML on-call, not the infra on-call, because the playbooks differ.

  • Three vendor-side savings levers cover most of the FinOps space: prompt caching (2024 GA on OpenAI, Anthropic, Gemini), batch APIs at ~50% rates, and cheaper-model routing via LiteLLM or Not Diamond.
  • The runaway-bill failure mode is real (Appendix G War Story 5); prevent it with a per-session cost SLO, a fast-burn alert, a hard kill switch, and prompt caching for shared prefixes.
