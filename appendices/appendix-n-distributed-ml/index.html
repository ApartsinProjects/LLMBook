Distributed ML

DDP, FSDP, ZeRO, Databricks, and Ray: the compute layer for training and serving when one GPU is not enough.

What this appendix is

The compute side of running ML at scale: parallelism strategies (data, parameter, pipeline, tensor, expert, sequence) plus the two managed platforms that absorb most of the operational complexity (Databricks for lakehouse-native ML, Ray for framework-agnostic distributed compute). Paired with Appendix M (Data Engineering) for the upstream data side and Appendix O (MLOps) for the operate side after deployment.

The chapter-level pretraining and scaling-laws motivation lives in Chapter 7. Section N.1 below is the practitioner counterpart: when you actually run the PyTorch launcher, which arguments produce DDP vs FSDP vs ZeRO-3, and which trade-offs each makes.

Library Shortcut
pip install torch                 # DDP / FSDP built-in
pip install deepspeed             # ZeRO-1/2/3, offload, MoE
pip install accelerate            # HuggingFace's launcher wrapper
pip install ray[train]            # Ray Train (PyTorch + JAX)
pip install ray[serve]            # Ray Serve (model deployment)
pip install ray[data]             # Ray Data (distributed dataloading)
# Databricks: access via web console + databricks-cli; no pip install needed.

Picking the right parallelism

If the model fits on one GPU and the dataset is large: data parallel (DDP). If the model fits if you shard parameters across N GPUs: FSDP or ZeRO-3. If the model is too large even sharded: pipeline + tensor parallelism (typically Megatron / DeepSpeed). The N.1 decision table lays out the memory math.
