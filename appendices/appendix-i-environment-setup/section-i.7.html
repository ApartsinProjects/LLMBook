I.7 API Keys and Secrets Management

Section under construction

This section is a placeholder for the secrets-handling material previously scattered across H.3 (Colab Secrets), I.1 (HF_HOME and HF_TOKEN tips), and I.5 (cloud-platform credential boxes). It will consolidate API-key management into one canonical home. The content below is a stub describing what the finished section will cover; the prose will be filled out in a subsequent pass.

Almost every LLM workflow eventually needs at least one credential: a HuggingFace token to download a gated model, an OpenAI or Anthropic key to call an API, a W&B token to log experiments, or a cloud-provider key to access object storage. This section is the single home for "where do I put my keys?" It covers local development, notebooks, cloud instances, CI environments, and the patterns that keep a key out of a Git commit. For the version-control discipline that catches leaked secrets after the fact, see Appendix J Section J.1.

Planned Coverage

  • The .env file plus python-dotenv. The default starting point: keep keys in .env, add .env to .gitignore, load with dotenv.load_dotenv(). Includes the .env.example template pattern for shareable repos.
  • HuggingFace tokens. HF_TOKEN environment variable, huggingface-cli login, and the HF_HOME cache-location override (migrated from I.1).
  • OpenAI / Anthropic / OpenRouter keys. OPENAI_API_KEY, ANTHROPIC_API_KEY, OPENROUTER_API_KEY conventions; per-project organization IDs; safe defaults for clients that auto-pick up env vars.
  • OS keyrings via keyring. Storing keys in macOS Keychain, Windows Credential Manager, or Linux Secret Service so they survive shell restarts without sitting in a plaintext .env.
  • Colab Secrets and notebook UX. Migrated from H.3: userdata.get("HF_TOKEN") patterns and the trade-offs of pasting keys into a Colab cell.
  • GitHub Codespaces and Repository Secrets. How to wire secrets into devcontainers so cloud-based development inherits the same environment as local.
  • Cloud-instance bootstrap. AWS Secrets Manager, GCP Secret Manager, and HashiCorp Vault for team setups; SSM Parameter Store for cheaper alternatives.
  • CI/CD secrets. GitHub Actions secrets.* usage that pairs with the model-deploy workflow in J.4, plus the standard list of "never log this" identifiers.
  • Leak detection and rotation. Pre-commit hooks (detect-secrets, gitleaks), what to do when a key ends up in Git history, and a sane rotation cadence.
Never commit a key

The single rule that prevents 99% of credential leaks: every secret lives in an environment variable, a keyring entry, or a managed secret store. Never a hard-coded string in a Python file, a notebook, or a config file that is tracked by Git. If you slip and commit a key, rotate it immediately; rewriting history does not erase the value from anyone who already cloned the repo.

Pairs with

The reproducibility checklist in Appendix J Section J.4 assumes your secrets are already managed correctly; without that, the same Git commit produces different results on different machines (or fails outright when an API key is missing).
