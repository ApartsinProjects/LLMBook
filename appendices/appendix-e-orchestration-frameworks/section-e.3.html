Haystack and DSPy: Pipelines and Programmatic Prompting

Section E.3

LangChain and LlamaIndex are the two frameworks most teams reach for first, but they are not the only options that have stayed in production through 2025-2026. Haystack (by deepset) and DSPy (Stanford NLP) represent two opinionated alternatives: Haystack treats LLM applications as typed DAG pipelines, optimizing for production reliability and observability; DSPy treats prompts as code that should be compiled from labeled examples rather than hand-written. Both have devoted user bases and both win specific bake-offs against the more general frameworks.

This section covers when to pick each. Haystack's typed pipelines and YAML serialization make it the right pick for enterprise teams that need reproducible deployments and component-level validation. DSPy's signature-and-optimizer paradigm makes it the right pick when prompt engineering is a bottleneck and you have a small labeled dataset to compile against. The cross-framework decision table in Section E.1 places them alongside LangChain and LlamaIndex; this section drills into the design choices that make each unique and shows the same retrieval-augmented Q&A task in both. The conceptual treatment of DSPy's signature framing lives in Chapter 14.5.2 (DSPy: Declarative Prompting with Optimizers); this section is the engineering counterpart.

Big Picture

Haystack 2.x and DSPy occupy opposite ends of the orchestration spectrum. Haystack is the most explicit framework on this list: every component has a typed schema, pipelines are validated at construction, and YAML serialization gives you a config-as-code artifact you can put in version control. DSPy is the most implicit: you write what you want, label some examples, run an optimizer, and let the framework generate the prompts. Both are right answers; they just solve different problems.

1. Haystack 2.x: Typed DAG Pipelines

Haystack 2.0 (released March 2024 after a multi-year rewrite of the original Haystack 1.x) is the deepset-maintained framework built around typed components connected into a pipeline DAG. Each component declares its input and output socket types; the pipeline validates at build time that connected sockets have compatible types and that all required inputs are wired. This is the strictest contract of any framework in this appendix and it pays off in the failure modes it eliminates: an entire class of "ran for an hour, then crashed because step 4 wanted a list and step 3 returned a single string" bugs simply cannot happen.

The library ships first-class components for indexing (writers and embedders for 15+ document stores), retrieval (dense, sparse, hybrid, and metadata-filter retrievers), and generation (chat generators for OpenAI, Anthropic, Bedrock, Vertex, Cohere, HuggingFace, and Ollama). The 2024-2025 roadmap added function-calling generators, structured output via Pydantic, and an Agent component that wraps a tool-using loop into a single pipeline node so you can compose agentic and non-agentic stages in one DAG.

from haystack import Pipeline
from haystack.components.embedders import OpenAITextEmbedder, OpenAIDocumentEmbedder
from haystack.components.retrievers import InMemoryEmbeddingRetriever
from haystack.components.generators.chat import OpenAIChatGenerator
from haystack.components.builders import ChatPromptBuilder
from haystack.dataclasses import ChatMessage
from haystack.document_stores.in_memory import InMemoryDocumentStore

store = InMemoryDocumentStore()
# ... index documents ...

rag = Pipeline()
rag.add_component("embedder", OpenAITextEmbedder())
rag.add_component("retriever", InMemoryEmbeddingRetriever(document_store=store))
rag.add_component("prompt", ChatPromptBuilder(template=[
    ChatMessage.from_user("Context: {{documents}}\n\nQuestion: {{query}}")
]))
rag.add_component("llm", OpenAIChatGenerator(model="gpt-4o-mini"))

# Typed connections: build fails if sockets don't match
rag.connect("embedder.embedding", "retriever.query_embedding")
rag.connect("retriever.documents", "prompt.documents")
rag.connect("prompt.prompt", "llm.messages")

result = rag.run({"embedder": {"text": "What is PagedAttention?"},
                  "prompt": {"query": "What is PagedAttention?"}})

The build-time validation means rag.connect("retriever.documents", "prompt.documents") raises immediately if those sockets don't have compatible types, rather than failing two retries deep in production. The other Haystack-specific advantages are YAML serialization (pipeline.dumps() emits a config-as-code file you can commit, diff, and load in production without rebuilding the graph in Python), native OpenTelemetry instrumentation (every component emits a span by default), and deepset Cloud, the managed offering for teams that want the framework but not the operations burden.

Production Pattern: Pipeline YAML in Git

Haystack's Pipeline.dumps() emits a YAML representation of the entire graph including component types, parameters, and wiring. Teams that have adopted Haystack at scale (the deepset customer case studies from 2024-2025 include Klarna, Airbus, and Deutsche Telekom) typically commit pipeline YAML to a separate repo, gate changes on code review, and load the YAML at service startup. This puts orchestration changes through the same review process as application code without rebuilding the container.

2. DSPy: Prompts as Compilable Programs

DSPy (stanfordnlp/dspy) takes a fundamentally different position: do not write prompts by hand. Instead, declare signatures (input/output specifications), compose them into modules (programs that call LLMs), provide a small labeled dataset and a metric, and let DSPy's optimizers (formerly called teleprompters) compile effective prompts from the data. The result is a system where prompt engineering becomes a search problem instead of an artisanal one, and where the artifact you ship is a compiled program, not a string.

The 2024 paper "DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines" (Khattab et al., ICLR 2024) showed that compiled DSPy programs match or beat hand-tuned chains-of-thought on multi-hop QA tasks while requiring less prompt engineering effort. The 2025 follow-up work on the MIPRO optimizer (Opsahl-Ong et al.) extended this to multi-stage prompt optimization with joint search over instructions and few-shot demonstrations; MIPRO is now the default optimizer for non-trivial DSPy programs.

import dspy
from dspy.teleprompt import BootstrapFewShot, MIPROv2

# 1. Configure the LM
dspy.configure(lm=dspy.LM("openai/gpt-4o-mini"))

# 2. Declare a signature (no prompt, just I/O contract)
class GenerateAnswer(dspy.Signature):
    """Answer questions with short factoid answers."""
    context = dspy.InputField()
    question = dspy.InputField()
    answer = dspy.OutputField(desc="A short factoid")

# 3. Compose a module
class RAG(dspy.Module):
    def __init__(self, retriever):
        self.retriever = retriever
        self.generate = dspy.ChainOfThought(GenerateAnswer)
    def forward(self, question):
        context = self.retriever(question, k=3).passages
        return self.generate(context=context, question=question)

# 4. Compile against a labeled dataset (50-200 examples is usually enough)
optimizer = MIPROv2(metric=exact_match_metric, num_candidates=10)
compiled_rag = optimizer.compile(RAG(retriever=my_retriever),
                                   trainset=trainset, valset=valset)

The compiled object is portable: you can save it (compiled_rag.save("rag.json")) and load it in production. The prompts inside are generated by the optimizer, often containing few-shot demonstrations selected via BootstrapFewShot and instructions refined via MIPRO. The 2025 DSPy ecosystem added a maturing assertion API (dspy.Suggest and dspy.Assert) that lets the compiler use runtime constraints during optimization, the SIMBA optimizer for very small training sets, and integrations with LangFuse and Phoenix for compiled-prompt observability.

Key Insight

DSPy's leverage point is not "no prompt engineering"; it is "no hand-written prompt engineering, with a measurable feedback loop." You still need a metric, a labeled trainset, and judgment about which signatures to declare. The win is that prompt iteration becomes a hyperparameter search you can rerun whenever the model changes, instead of a manual rewrite.

The decision is more about team and workflow than features. Pick Haystack when reproducibility, typed pipelines, and YAML-in-Git matter, typically large engineering organizations with strict change-management. Pick DSPy when you have a measurable metric, a small labeled dataset, and you are tired of rewriting prompts every time a model version changes; classic fits are multi-hop QA, factuality-critical workflows, and reasoning chains that benefit from optimizer-found few-shots. Pick LangChain when ecosystem breadth and rapid iteration are paramount and you accept the looser typing as a trade.

DSPy Caveat: Optimizers Need a Metric

DSPy buys you nothing if you cannot articulate a metric and assemble a labeled dataset. For pure free-form generation tasks (creative writing, open-ended summarization without ground truth), there is no signal for the optimizer to chase and the framework reduces to a verbose way to write zero-shot prompts. Use DSPy when you have an evaluable metric (exact match, F1, factuality classifier, LLM-judge with high IRR) and 50+ labeled examples. Below that threshold, hand-written prompts are usually faster.

4. Interoperability: They Compose

A subtle point that gets lost in framework wars: nothing prevents you from using these tools together. A common 2025 pattern is to use DSPy to compile the prompts that get hand-pasted into a Haystack ChatPromptBuilder or a LangChain PromptTemplate. Treat DSPy as the prompt compiler and the heavier framework as the production runtime. Conversely, a Haystack pipeline can call a DSPy-compiled module as a custom component if you want both the typed-DAG structure and the optimized prompts.

5. Production Cases

Haystack's customer list (publicly disclosed in 2024-2025 deepset blog posts) includes Airbus for technical-documentation search, Deutsche Telekom for internal IT-support agents, and Klarna for customer-service routing; deepset Cloud is the common managed-deployment vehicle. DSPy's adoption has skewed academic and frontier-lab: the original Khattab et al. paper showed multi-hop QA wins on HotpotQA, and the 2024-2025 work from Together AI and Databricks used DSPy to compile prompts for retrieval pipelines on production support chatbots. JetBlue's 2024 case study (described at the AI Engineer Summit) showed a DSPy-compiled customer-routing classifier outperforming the hand-written predecessor on the same evaluation set while requiring no manual prompt edits across two model upgrades.

Key Takeaway
  • Haystack 2.x is the strictest mainstream orchestration framework. Typed DAG pipelines, build-time validation, YAML serialization, and native OpenTelemetry make it the right pick for enterprise teams that need reproducible deployments and component-level review.
  • DSPy replaces hand-written prompts with compiled programs. Declare a signature, provide a labeled dataset, run BootstrapFewShot or MIPROv2, and ship the compiled artifact; prompts become a search-and-optimize problem instead of an artisanal one.
  • Pick Haystack for strict-review enterprise RAG, DSPy for optimizable prompts with measurable metrics, and LangChain for broad ecosystem coverage and rapid iteration. The three are not mutually exclusive: DSPy-compiled prompts pasted into Haystack pipelines is a common 2025 pattern.
  • DSPy without a metric and a labeled dataset reduces to a verbose zero-shot framework. The optimizer is the value; don't reach for DSPy if you cannot articulate what "better" means.
  • Both frameworks integrate with the broader 2025-2026 ecosystem (OTel observability, Pydantic structured output, MCP tools), so the choice does not lock you out of the rest of the stack.
