Deployment Patterns

Section N.3
What this section is

The reference for rolling out a new model version, a new prompt, or a new agent without breaking production. Four patterns (canary, blue-green, shadow, A/B test) plus feature flags for prompts together cover every safe-rollout scenario in an LLM stack. We walk each pattern, the tools that ship it (GitOps with ArgoCD, Flagger, LaunchDarkly, vendor-native A/B in LangSmith and Langfuse), and the decision rule for picking among them.

The conceptual treatment of production engineering and rollout strategy lives in Chapter 35 (Production Engineering). This section is the operational counterpart: which Kubernetes resource you actually apply, which flag-evaluation latency you should worry about, and how the patterns combine with the monitoring loop from Section N.2. Cross-references to Appendix K (Inference Serving) for the underlying serving infrastructure and Appendix O (Docker and Containers) for the image-promotion mechanics are flagged inline.

O.3.1 The Four Rollout Patterns

Each pattern answers a different question about risk and observability. Picking the right one is more about what you can measure before users see the new version than about the deployment mechanics themselves.

Canary: route a small fraction of live traffic (typically 1%, then 5%, then 25%, then 100%) to the new version while keeping the old version serving the rest. You compare error rates, latency, and eval-in-prod quality scores between the two cohorts. Canary is the right default when you trust your monitoring to detect a regression within the canary window. It is cheap, reversible, and produces a clean A/B comparison for the metrics you instrumented.

Blue-green: stand up the new version (green) in parallel to the current production (blue), point your load balancer at green in a single cutover, and keep blue warm for instant rollback. There is no traffic-split phase; the comparison is between empty and full traffic. Blue-green wins when you cannot tolerate a mixed-version cohort (e.g., a multi-turn agent where the same user must not hit different versions across turns) or when the new version requires schema changes that cannot coexist with the old one.

Shadow mode: mirror live requests to the new version but discard its responses; users see the old version's output. The new version sees real traffic and you can measure its behavior offline (latency, response distribution, eval-in-prod quality) without exposing users to its mistakes. Shadow is the right choice for high-stakes changes (a new base model, a major prompt overhaul) where you want production-load characterization before any user impact.

A/B test: deliberately split traffic between two versions and measure a user-level outcome (CSAT, task completion, downstream conversion) with statistical power. Unlike canary, A/B is not about catching regressions, it is about deciding which version is better on a metric that takes days or weeks to accumulate signal.

Key Insight

Canary and A/B look similar from 30,000 feet but answer different questions. Canary asks "is the new version safe to roll out?" and runs for hours; A/B asks "which version maximizes outcome X?" and runs for days to weeks. Conflating them produces noisy results: a 24-hour canary cannot detect a CSAT lift, and a two-week A/B can be sabotaged by a bug that should have been caught in canary on day one.

O.3.2 Feature Flags for Prompts and Model Versions

The classic feature-flag pattern (Stripe, LaunchDarkly, OpenFeature) becomes more useful in LLM stacks because the unit of change is often not code but text: a prompt template, a few-shot example list, a model identifier, a temperature value. Treating these as flags lets you change behavior in seconds without a deploy, and lets you scope a change to a user segment ("internal employees only", "10% of free-tier users", "all enterprise on plan tier 3").

LaunchDarkly and OpenFeature are the vendor and OSS standards for general feature flags; both work for prompts but lack LLM-aware tooling. Langfuse prompt management and LangSmith's prompt registry are LLM-native: they version prompts as first-class artifacts, support A/B variant labels per prompt, and emit usage telemetry tied to the prompt version so you can correlate a quality dip to a specific edit. Helicone added prompt experiments in 2024 with similar semantics scoped to its proxy.

from langfuse import Langfuse

lf = Langfuse()
# Prompt registered with two variants; Langfuse routes by user_id hash
prompt = lf.get_prompt(
    name="refund-policy-summarizer",
    label="production",  # or "canary", "experiment-a", etc.
    cache_ttl_seconds=300,
)
messages = prompt.compile(policy_text=POLICY, user_question=q)
# Emits a span linked to the exact prompt version used
response = openai_client.chat.completions.create(
    model="gpt-4o-2024-11-20",
    messages=messages,
)

O.3.3 GitOps and Progressive Delivery on Kubernetes

For self-hosted inference (vLLM, TGI, Ollama, custom servers from Appendix K) the standard 2024-2026 stack is GitOps with progressive delivery: ArgoCD reconciles Kubernetes manifests from a Git repository, and Flagger drives the canary or blue-green progression with automated metric checks. The model artifact is a container image (built per Appendix O); the rollout is a Kubernetes Deployment with a Flagger Canary resource that defines the traffic-shift schedule and the success thresholds.

A minimal Flagger canary for a vLLM deployment looks like this:

apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: llm-inference
spec:
  targetRef: {apiVersion: apps/v1, kind: Deployment, name: vllm-server}
  service:
    port: 8000
  analysis:
    interval: 1m
    threshold: 5         # how many failed checks before rollback
    maxWeight: 50        # peak canary share before promotion
    stepWeight: 5        # +5% traffic per interval
    metrics:
      - name: request-success-rate
        thresholdRange: {min: 99}
        interval: 1m
      - name: request-duration-p99
        thresholdRange: {max: 2000}  # ms
        interval: 1m
      - name: faithfulness-score      # custom Prometheus metric from Ragas
        thresholdRange: {min: 0.85}
        interval: 5m

The third metric, faithfulness-score, is the LLM-specific addition: a Prometheus exporter scrapes the Ragas judge from Section N.2 and Flagger refuses to promote if quality dips. This composition is what closes the loop between drift detection and deployment automation.

CanaryLow (small cohort)Minutes to hours1-25% during rolloutMost model and prompt updates

Shadow modeNone (no user impact)Hours to days0% (mirrored only)New base model, major prompt rewrite
A/B testMedium (planned split)Days to weeks50% per arm typicallyComparing variants on user outcome
Feature flagLow (instant toggle)Real-timeTargeted segmentsQuick prompt edits, per-tenant config
Tip: Combine, Do Not Pick

The patterns compose. A typical major-version rollout uses shadow for the first 48 hours to characterize the new version under production load, then canary for the first user-visible promotion with Flagger driving the traffic shift, then a feature flag to keep a per-tenant override available for the first month after full rollout. A/B testing layers on top when you have multiple equally safe variants and need to pick a winner on a longer-horizon metric.

O.3.5 Real-World Vendor Cases

Three named 2024-2025 cases. GitHub Copilot's 2024 technical posts described shadow-mode rollouts of new base models for several weeks before user exposure, with a custom completion-acceptance metric as the promotion gate. Notion AI described using LaunchDarkly for prompt-level feature flags during their 2024 AI expansion, citing the ability to roll back a misbehaving prompt in seconds. Cursor's late-2024 engineering posts attributed their handling of model-vendor outages to a Flagger-driven blue-green setup that swapped providers via DNS-level traffic shift within 90 seconds of an alert. Key Takeaway
  • Four rollout patterns cover the production LLM space: canary (gradual traffic shift), blue-green (cutover with rollback), shadow (mirrored offline eval), A/B test (long-horizon outcome comparison).
  • Feature flags (LaunchDarkly, OpenFeature) and LLM-native prompt registries (Langfuse, LangSmith) let you change prompts and model identifiers in seconds without a code deploy.
  • GitOps with ArgoCD + Flagger is the standard self-hosted stack; the LLM-specific addition is a custom quality metric (Ragas faithfulness, eval-in-prod score) as a Flagger promotion gate.
  • The patterns compose: shadow for new base models, canary for user-visible promotion, feature flags for per-tenant override, A/B test for variant comparison. Production teams use all four.
  • Pair every deployment pattern with the drift-detection loop from Section N.2: deployments and drift signals are two sides of the same control loop.
