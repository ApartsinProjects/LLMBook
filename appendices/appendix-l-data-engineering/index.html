Data Engineering

PySpark, Delta Lake, feature stores, and production data pipelines: the data substrate every LLM application sits on top of.

What this appendix is

Every production LLM system is, underneath, a data system. Training corpora need to be cleaned, deduplicated, and versioned. Embeddings need to be regenerated and indexed when models change. Retrieval pipelines need fresh, governed data. Online features (recent user actions, document freshness signals, A/B-test arm assignments) need to be served with millisecond latency. This appendix collects the data-engineering layer of the production stack: PySpark for large-scale text processing, Delta Lake for ACID-versioned data lakes, feature stores for online + offline parity, and the production pipeline patterns that tie ingestion to serving.

The data-engineering view is distinct from Distributed ML (Appendix M) which handles the compute side of large-scale training, and from MLOps (Appendix N) which handles the operate-side after deployment. Appendix L is the upstream substrate; N is the training engine; O is the production lifecycle.

When to read this

Read sections M.1 and M.2 when you are preparing a training corpus or building a retrieval index over a non-trivial document set. Read M.3 when your application needs sub-second feature lookups (recommendation, personalization, real-time scoring). Read M.4 before you wire a research notebook into a recurring scheduled job. For the compute side of scale, jump to Appendix M (Distributed ML).

What Comes Next

With the data layer in place, Appendix M (Distributed ML) shows how to take the cleaned corpora and trained embeddings off your laptop and into multi-GPU / multi-node compute. From there, Appendix N (MLOps) covers what happens once the model is live.
