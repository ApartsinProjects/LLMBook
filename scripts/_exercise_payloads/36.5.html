Exercise 36.5.1: Why Vertical Slices Conceptual

You have two prototype strategies for an AI feature: (a) build the data pipeline first, then the model, then the UI; (b) build a one-screen end-to-end flow and refine it. (a) Why does the vertical-slice approach almost always beat the bottom-up approach for AI products? (b) What is the only situation where bottom-up is correct? (c) What is the typical number of vertical-slice iterations before MVP?

Answer Sketch

(a) AI feature feasibility depends on the interaction between data, model, and UI; you can't predict it without running the full path. A vertical slice surfaces the integration risks (latency budget, prompt format, error UX) on day one. Bottom-up may have you build a perfect pipeline before discovering the model doesn't pass feasibility. (b) Bottom-up wins only when the pipeline is the product itself (a data quality service, an indexer for a known model) or when the model and UI are already proven. (c) Typical: 5-15 vertical-slice iterations before MVP, each measured in days. Each iteration tests one risky hypothesis end-to-end. If you're past 20 iterations without convergence, the issue is probably the role assignment (Section 36.2), not the model.

Exercise 36.5.2: Predict Build-Measure-Steer Velocity Predictive

You set up the build-measure-steer loop with: (i) a 50-item eval set, (ii) a CI pipeline that runs the eval on every commit, (iii) an LLM coding assistant. Predict: (a) iteration cycle time; (b) the bottleneck after the first week; (c) what slows the loop most as the project ages.

Answer Sketch

(a) Cycle time of 10-30 minutes per iteration is achievable: the LLM proposes a change in seconds, CI runs the eval in 1-5 minutes for 50 items, you read the delta and decide. (b) After a week, the bottleneck is human attention: there are more eval signals than you can review. Solution: dashboards, regression alerts, sample-based deep-dives. (c) Aging slowdowns: (1) eval set drift relative to user reality requires periodic refresh; (2) eval set bloat (too many items) makes CI slow, so you need stratified sampling; (3) coupled changes (one PR fixes A but breaks B) require structural refactoring that LLM assistants don't always do well. Re-investing in the harness every 6-8 weeks keeps velocity high.

Exercise 36.5.3: Minimal Eval Harness Code Tweak

Sketch a 15-line evaluation harness in pure Python: it loads a JSONL of (input, expected) records, runs the system on each input, computes per-record success with a pluggable scorer, and prints aggregate metrics + a CSV per-record diff log. State two scorer options for an extraction task.

Answer Sketch

import json, csv, sys
from system import run
from scorers import scorer_exact, scorer_f1
scorer = scorer_f1 # or scorer_exact
records = [json.loads(l) for l in open("eval.jsonl")]
rows, total, hits = [], 0, 0
for r in records:
  actual = run(r["input"])
  score = scorer(actual, r["expected"])
  rows.append({**r, "actual": actual, "score": score})
  total += 1; hits += (score >= 0.5)
print(f"pass@score>=0.5: {hits}/{total}")
w = csv.DictWriter(sys.stdout, fieldnames=rows[0].keys()); w.writeheader(); w.writerows(rows)
Two scorers for extraction: (1) exact match on the structured field (strict, useful for IDs and codes); (2) token-set F1 against a normalized form (looser, useful for free-text spans like names or dates). Always emit per-record output so you can inspect failures, not just the aggregate.

Exercise 36.5.4: Coding-Assistant Trust Failures Failure Mode

You use an AI coding assistant in tight loops. List four trust failure modes that cost more than they save, with one mitigation each.

Answer Sketch

(1) Plausible-but-wrong refactors: the assistant rewrites a module to "improve" it but breaks subtle invariants (timezone handling, encoding). Mitigation: require regression tests on the rewritten module before accepting. (2) Spec drift: the assistant interprets "fix the bug" liberally and adjusts unrelated code. Mitigation: small, scoped diffs only; reject any PR larger than ~50 lines unless explicitly requested. (3) Hallucinated APIs: the assistant calls library functions that don't exist or have different signatures. Mitigation: lint and type-check on every diff; CI rejects unresolved imports. (4) Over-confidence in passing tests: tests pass but the test set is too small to validate the change. Mitigation: explicit eval-suite gate (Exercise 36.5.3), not just unit tests. The recurring lesson: coding assistants need the same "trust but verify" instrumentation as LLM features themselves.
