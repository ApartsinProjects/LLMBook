Exercise 2.1.1: Vocabulary Tradeoff Math Calculation

You are choosing between three vocabulary sizes for a new model: V = 1,000 (character-level), V = 32,000 (subword), V = 200,000 (word-level). Assume the embedding layer is V x 1024 and the output projection is also V x 1024 (tied). (a) How many parameters does the embedding-plus-projection block contain in each case? (b) Suppose the average sequence is 500 characters. How many tokens does that produce in each scheme (estimate)? (c) For a fixed compute budget, which scheme spends more on attention and which spends more on embeddings, and why does this matter at scale?

Answer Sketch

(a) With tied embeddings, parameter count is V * 1024. Char: 1.0M; subword: 32.8M; word-level: 204.8M. (b) Char: ~500 tokens. Subword (~4 chars per token average for English): ~125 tokens. Word-level (~5 chars including spaces): ~100 tokens. (c) Char-level produces long sequences (500 tokens) so attention cost scales as $500^2$ per layer; word-level produces short sequences but pays 200x more in embedding parameters. Subword balances both, which is why every modern LLM lives in the 30k-200k vocabulary range. At 1B-parameter scale, the embedding block of word-level tokenization would consume 20% of the entire parameter budget without any improvement in downstream quality.

Exercise 2.1.2: The Multilingual Token Tax Calculation

The "Multilingual Token Tax" warning shows that the same sentence in English costs ~10 tokens but the Hindi translation costs ~50 tokens with the GPT-4 tokenizer. (a) Compute the multiplicative cost penalty for serving Hindi users at API pricing of $5/M input tokens. (b) The same penalty appears at inference latency. Why? (c) Name two technical mitigations a product team can deploy without retraining the model.

Answer Sketch

(a) The Hindi user pays 5x as much per equivalent semantic content. If your monthly budget supports 1M English queries, the same budget supports 200k Hindi queries. The cost penalty compounds because both prompt and response are inflated. (b) Latency scales roughly linearly with token count for input and is exactly proportional for output (one forward pass per generated token). A 5x token expansion implies a 5x increase in time-to-first-token and time-to-completion at fixed model size. (c) Mitigations without retraining: (i) Switch to a model with a more multilingual tokenizer (Llama-3, Gemini, Aya). The choice of tokenizer is not the choice of model. (ii) Translate user input to English server-side, run inference in English, translate output back. This adds two cheap MT calls but cuts the LLM cost. The fundamental fix is a balanced multilingual tokenizer trained with proportional language sampling, which requires retraining.

Exercise 2.1.3: Why LLMs Fail at Arithmetic Failure Mode

The "Why LLMs Struggle with Math" note links arithmetic failures to tokenization. (a) Show how "1234567" might tokenize differently than "1,234,567" or "1 234 567" in a typical BPE tokenizer, and why this matters for digit-by-digit reasoning. (b) Llama-3 forces digit-level tokenization for numbers. Predict its arithmetic accuracy gain over Llama-2 on multi-digit addition, qualitatively, and explain. (c) Why doesn't this fix help with division and other compositional operations?

Answer Sketch

(a) "1234567" might tokenize as ["123", "4567"] or ["12", "345", "67"] depending on training-data frequencies. The same digits in "1,234,567" produce different tokens because of the comma. So the model sees the same number as completely different token sequences depending on formatting, which means it cannot transfer learned arithmetic across surface forms. (b) Forcing digit-level tokenization yields large gains (~20-40 percentage points) on multi-digit addition because the model now sees a stable representation: every number is the same sequence of seven single-digit tokens regardless of formatting. The carry pattern can be learned once and applied universally. (c) Division and multiplication are not local-pattern operations; they require holding intermediate state across the entire number, which a transformer's single forward pass cannot do well. Tokenization fixes the input representation but not the algorithmic limit. Tool use (calling a calculator) is the production solution.

Exercise 2.1.4: The Trailing-Space Trap Code Tweak

The "Trailing Space Problem" subsection explains that " hello" and "hello" tokenize to different IDs in many tokenizers. (a) Construct a concrete prompting bug that this causes. (b) Why does adding a trailing space to the prompt before generation often make the output worse, not better? (c) What is the standard fix that frameworks like vLLM apply automatically?

Answer Sketch

(a) You write a few-shot prompt as "Q: ... A: " (with trailing space) and the model generates garbage. The training data shows "A:" followed by " response", where the leading space is part of the response token; by including the space in your prompt, you have committed the model to a specific token boundary that may not exist in the embedding table or that splits awkwardly. (b) The trailing space inflates the prompt by one token whose embedding is not where the next-token distribution expects to be conditioned. The model effectively sees "you have just emitted a lone space token, what comes next?" and answers with low-probability noise. (c) Frameworks normalize by stripping trailing whitespace from the prompt and letting the model emit the leading space as part of its first generated token. The general rule: prompts should end where the model is naturally about to generate a new token boundary, not in the middle of one.
