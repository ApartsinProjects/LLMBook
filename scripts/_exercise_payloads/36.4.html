Exercise 36.4.1: Observe-Steer vs Plan-Execute Conceptual

The classic engineering loop is plan-then-execute. The Observe-Steer loop is observe-then-adjust. (a) Why does plan-execute fail when the build artifact is partially generated by an LLM? (b) What does observe-steer require that plan-execute doesn't? (c) When does plan-execute still win?

Answer Sketch

(a) Plan-execute assumes the executor (developer) implements the plan deterministically. With an LLM in the loop, the executor's behavior is probabilistic and partially opaque, so any plan written in advance is partly fiction; you discover what was actually built only by running it. (b) Observe-steer requires fast feedback loops: tests, metrics, and visible logs you can read and react to in minutes, not days. The whole velocity advantage depends on closing the loop quickly. (c) Plan-execute still wins when the artifact is fully deterministic (a SQL migration, a config file change) and when the cost of being wrong is high (production data loss). For LLM-generated code or content, observe-steer is the better fit.

Exercise 36.4.2: Predict the Vibe-Coding Failure Curve Predictive

You vibe-code a feature in 3 hours that would have taken 3 days the traditional way. Predict: (a) the qualitative shape of the maintenance cost over the next 6 months; (b) when does the cumulative cost cross the traditional cost; (c) what single discipline most slows the cost growth?

Answer Sketch

(a) Maintenance cost rises super-linearly: vibe-coded artifacts often lack structure, tests, and documentation, so each subsequent change costs disproportionately more time. (b) Crossover usually happens within 4-12 weeks for non-trivial features; the initial 10x speedup pays for itself only if the feature is short-lived or doesn't need iteration. (c) The single highest-leverage discipline: write the eval harness before you accept any LLM-generated code. The eval becomes the steering wheel; without it, every change is a roll of the dice and maintenance cost compounds. Add minimal documentation and a smoke-test suite and you preserve most of the speed advantage.

Exercise 36.4.3: Wire Up an Observation Channel Code Tweak

Sketch a 10-line addition to a Python LLM-generated service that emits structured observation events to stdout: every LLM call's prompt-hash, latency, token counts, and a coarse outcome label (success, error, refusal). State why you don't log full prompts by default.

Answer Sketch

import json, hashlib, time
def emit(event, **kw): print(json.dumps({"ts": time.time(), "event": event, **kw}))
def call(model, prompt):
  t0 = time.time(); h = hashlib.sha256(prompt.encode()).hexdigest()[:12]
  try: r = llm.chat(prompt); outcome = "ok" if r.content else "empty"
  except Exception as e: r = None; outcome = "error"
  emit("llm_call", model=model, prompt_hash=h, latency_ms=int((time.time()-t0)*1000),
    tokens_in=getattr(r, "usage", {}).get("input", None), tokens_out=getattr(r, "usage", {}).get("output", None), outcome=outcome)
  return r
Why hash, not full text: production prompts often contain user PII or proprietary data; logging the hash plus token counts gives you all the trend signal (cost, latency, error rate, prompt diversity via hash distribution) without storing sensitive content. Sample full prompts under explicit consent or in a separate, access-controlled audit log.

Exercise 36.4.4: Steering Without Observation Failure Mode

Three teams adopt vibe-coding. Team A ships first and breaks production weekly. Team B ships slowest but smoothest. Team C ships fast and breaks rarely. List the practices that distinguish each, and what the worst pattern is.

Answer Sketch

Team A vibe-codes without an eval suite or smoke tests; they accept LLM output blindly and discover bugs in production. Team B over-corrects with manual review of every diff, losing the speed advantage entirely. Team C invests upfront in a small eval suite and a CI smoke-test pipeline; LLM-generated changes must pass the gate before merge. The worst pattern is Team A's: speed-only without observation. The bug rate compounds, oncall burns out, and trust in LLM tooling collapses across the org. Team C's pattern (eval-as-steering) is the sustainable optimum: ~80% of A's speed with ~10% of A's incidents.
