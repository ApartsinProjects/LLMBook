Exercise 38.4.1: Continuous vs One-Shot Eval Conceptual

Pre-launch eval is one-shot. Production eval is continuous. (a) Name three sources of quality drift that can only be detected continuously. (b) Why is the production eval set typically different from the pre-launch eval set? (c) What is the minimum eval cadence for a production LLM feature, and why?

Answer Sketch

(a) Drift sources: (i) input distribution shift (users learn what works and migrate to harder cases), (ii) silent provider model updates, (iii) data-source changes (knowledge base, tool APIs, retrievers). (b) Production eval is built from sampled, representative real interactions; pre-launch eval is built from hand-curated cases optimized for coverage. The two sets answer different questions: "is this feature ready?" vs "is it still working?" (c) Minimum cadence: nightly for the headline metric, weekly for the comprehensive eval. Less frequent and you'll miss a regression by days; more frequent rarely improves detection but doubles infrastructure cost. Tie cadence to typical incident-detection time, not to availability of compute.

Exercise 38.4.2: Predict the Drift-Detection Lag Predictive

You set up drift detection that compares this week's eval scores to a 4-week rolling baseline. Predict: (a) the typical detection lag for a sudden 10-point quality drop; (b) the typical detection lag for a slow 1-point/week decline; (c) which is more dangerous to your users.

Answer Sketch

(a) Sudden 10-point drop: detected in 1-3 days because it's far outside baseline noise; alert fires immediately on the first nightly eval. (b) Slow 1-point/week: typically detected at 4-8 weeks of cumulative drift, when the difference exceeds the baseline's natural variance. The slow drift can rack up 5-10 points before the detector trips. (c) Slow decline is more dangerous: by the time you detect it, large numbers of users have had degraded experiences, customer-support tickets have piled up, and the cause is harder to root-cause because there's no single change-point to investigate. Mitigations: track per-week diffs explicitly, not just window-vs-baseline; complement with a control eval that's intentionally easy and should never drop, providing a "canary" signal for the harder eval.

Sketch a 12-line A/B test runner for a prompt change. The runner should: (a) split traffic 50/50 by user_id hash, (b) record (variant, query, response, score) per request, (c) report a t-test on the score difference after N samples. State the most common A/B mistake teams make for LLM features.

def variant(uid): return "A" if int(hashlib.md5(uid.encode()).hexdigest(), 16) % 2 == 0 else "B"

  t, p = ttest_ind(a, b); print(f"meanA={sum(a)/len(a):.3f} meanB={sum(b)/len(b):.3f} p={p:.4f}")
Most common mistake: peeking. Teams check the test daily and stop as soon as it looks significant, inflating false-positive rate. Fix: pre-register the sample size and only test once at the end (or use sequential testing methods that account for repeated looks).

Exercise 38.4.4: Iteration Failure Modes Failure Mode

You run a continuous improvement loop on an AI feature. List four failure modes that quietly degrade the loop over time, with one mitigation each.

Answer Sketch

(1) Eval rot: the eval set was sampled six months ago and no longer reflects user inputs. Mitigation: refresh 20% of the eval set every quarter from recent logs. (2) Goodhart's law: the team optimizes the eval metric until the metric and quality decouple (e.g., longer answers always win the metric, even when worse). Mitigation: rotate scoring rubrics and add periodic human spot-checks. (3) Confirmation-bias change-management: every change ships if it improves the metric, even by 0.1 points; the team stops investigating regressions because "the trend is up." Mitigation: require both improvement and stable per-segment scores before promoting. (4) Provider-side change overwhelm: the provider rolls 3 model updates in a quarter; the team can't keep up with re-baselining. Mitigation: pin to dated model snapshots and adopt new versions on a planned cadence, not on the provider's schedule.
