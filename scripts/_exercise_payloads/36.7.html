Exercise 36.7.1: Prototype-to-MVP Readiness Conceptual

You have a working prototype. List four "graduate to MVP" gates that go beyond "the prototype works on demo inputs", and explain why each gate exists.

Answer Sketch

(1) Eval set covers the user input distribution: prototypes are tested on builders' inputs; real users send different distributions. Without the eval expansion, you ship blind. (2) Latency and cost meet SLOs at expected QPS: a prototype tested at 1 req/min may collapse at 100 req/min due to rate limits or cold-start tail latency. (3) Failure handling and degradation paths exist: what happens when the LLM API returns 429 or 500? Prototypes typically crash; MVPs degrade gracefully. (4) Observability and on-call runbook: someone has to be paged when this breaks; if no one knows how to debug it at 2am, it's not MVP-ready. The four gates correspond to the four production failure classes: distributional, performance, reliability, operational.

Exercise 36.7.2: Predict the Quality Gate Tightness Predictive

For each role, predict the appropriate per-task quality threshold an MVP should meet before launch: (a) copilot suggesting code edits; (b) autopilot issuing customer refunds; (c) drafter producing marketing copy. State why the thresholds differ.

Answer Sketch

(a) Copilot: ~70-80% useful-suggestion rate is plenty; users review and reject easily. Acceptance threshold is moderate because reversibility is high and the human is in the loop. (b) Autopilot refunds: ~99%+ correctness on the refund decision, plus a hard cap on refund amount and a per-day budget guardrail. The high threshold reflects irreversibility and audit obligation; the guardrails bound blast radius even when the model is wrong. (c) Drafter for marketing copy: ~90% acceptable-style outputs, with a human editor adding final polish. The threshold is moderate but the failure mode (off-brand voice) is a slow leak rather than a single-incident risk. The general rule: quality threshold = f(reversibility, blast radius, presence of human reviewer).

Exercise 36.7.3: Add a Fallback Tier Code Tweak

Sketch a 10-line wrapper that calls a frontier LLM, falls back to a smaller model on rate-limit, and finally falls back to a static "we couldn't generate a response right now" message. Include logging that lets you measure each tier's hit rate.

Answer Sketch

def respond(prompt, log):
  for tier, fn in [("primary", call_gpt4), ("secondary", call_haiku), ("static", lambda p: "We could not generate a response. Please try again.")]:
    try:
      r = fn(prompt)
      log({"tier": tier, "outcome": "ok"})
      return r
    except Exception as e:
      log({"tier": tier, "outcome": "fail", "err": str(e)})
      continue
The tier-hit-rate metric (primary 95% / secondary 4% / static 1%) becomes a first-class SLO. If secondary or static creep up, you have a quality regression and a customer-experience bug at the same time. The tiered pattern is what separates "demo grade" from "MVP grade".

Exercise 36.7.4: Premature MVP Failure Modes Failure Mode

You ship MVP after passing the prototype gate but before the four graduate gates. List three classes of incident that follow and how each erodes trust differently.

Answer Sketch

(1) "It worked yesterday and broke today": provider-side model update changes behavior, your eval gate didn't catch it, and a customer files a support ticket. Erodes trust in the brand. (2) Scale collapse: traffic spike triggers rate limits, latency balloons to 30 seconds, half the requests time out. Erodes trust in reliability. (3) Mis-handled edge case: a niche user input triggers a confidently wrong output, gets shared on social media. Erodes trust in safety. The three classes share one root cause: shipping before observability and gates exist. Recovery costs (incident response, customer apologies, brand repair) usually exceed the cost of the gates by 5-50x. The "graduate gates" are insurance, not bureaucracy.
