Exercise 0.3.1: Broadcasting Trap Failure Mode

The "Silent Shape Bugs" warning notes broadcasting can produce wrong results without errors. Predict the output shape and a likely bug: (a) a = torch.randn(32, 1), b = torch.randn(32), then a + b. (b) logits = torch.randn(8, 10), targets = torch.randn(8, 1), then F.cross_entropy(logits, targets). (c) Sketch a 1-line PyTorch idiom that asserts a tensor has the expected shape and fails loudly if not.

Answer Sketch

(a) Shape (32, 32). PyTorch broadcasts a as (32, 1) and b as (1, 32) -> (32, 32). The likely bug: the user wanted element-wise addition of two 32-length vectors, expected shape (32,) or (32, 1), and silently produced an outer-product-shaped result that crashes 50 lines downstream. (b) F.cross_entropy expects integer class indices of shape (8,), not float targets of shape (8, 1). This raises a runtime error in modern PyTorch but used to silently misalign in older versions. The fix: targets = targets.long().squeeze(-1) or pass class indices directly. (c) assert tensor.shape == (32, 768), f"got {tensor.shape}". A more rigorous variant is einops' rearrange(x, 'b s d -> b s d') or torchtyping, both of which catch shape regressions at the call site rather than 100 lines later. The "Common Mistakes" section at 0.3.8 elaborates several more.

Exercise 0.3.2: Why Zero the Gradients Conceptual

The vignette "Forgetting to Zero Gradients Corrupts a Language Model" describes the classic optimizer.zero_grad() bug. (a) Explain in one sentence what happens to the parameter updates if you forget the call. (b) The PyTorch design accumulates gradients by default rather than overwriting. Name two legitimate use cases this enables. (c) PyTorch 1.7+ added set_to_none=True as the recommended argument. What concrete benefit does this give over the default?

Answer Sketch

(a) Each backward() call adds to the existing .grad tensor, so by step k you are doing an SGD update with the sum of gradients from all k previous steps, which means an effective learning rate that grows linearly with step count. The model's loss explodes within a few hundred iterations. (b) Legitimate uses: (i) gradient accumulation, where you do N backward() calls then one step(), simulating a larger batch size on memory-limited hardware; (ii) higher-order or composed loss objectives where multiple losses are backpropagated separately and combined. (c) set_to_none=True deallocates the .grad tensors instead of zeroing them in place. This saves memory (the tensors do not exist between steps), runs slightly faster (no kernel launch to write zeros), and is now the documented default in PyTorch 2.x. The only behavior change to watch for: tensor.grad returns None instead of a zero tensor, so any code that reads gradients must handle the None case.

Exercise 0.3.3: Mixed Precision Math Calculation

The mixed-precision section describes torch.amp. Suppose you train a 7B-parameter model in float32 and want to switch to bfloat16. (a) Estimate the parameter memory before and after. (b) Why does bfloat16 not cause the loss-scaling issues that float16 does? (c) Why is the optimizer state still kept in float32 in standard mixed-precision recipes, and what does this imply about total memory savings?

Answer Sketch

(a) 7B params at 4 bytes (float32) = 28 GB. At 2 bytes (bfloat16) = 14 GB. (b) bfloat16 uses 8 exponent bits matching float32's range, so gradients underflow at the same threshold as float32; only mantissa precision (3 vs 23 bits) is lost. float16 has only 5 exponent bits and saturates at gradient magnitudes that occur routinely during training, which is why GradScaler exists. bfloat16 needs no scaling. (c) Adam's first and second moment estimates (m, v) plus the master parameter copy are kept in float32 because their magnitudes span many orders and small accumulation errors compound. Adam's state is 2x the parameter count, so the optimizer alone takes 7B * 2 * 4 = 56 GB regardless of forward-pass precision. Total: 14 GB params + 56 GB optimizer + activations. Mixed precision halves activation memory and roughly halves forward/backward FLOPs, but the optimizer dominates total memory; that is why ZeRO-style parameter sharding targets the optimizer first.

Exercise 0.3.4: torch.compile Sharp Edges Failure Mode

Section 0.3.7.1 describes torch.compile as a one-line speedup. Name three failure modes that cause silent slowdowns or errors, and one diagnostic command for each.

Answer Sketch

(1) Recompilation thrash: dynamic input shapes trigger recompilation on every step, making the compiled model slower than eager. Diagnose with TORCH_LOGS=recompiles python script.py; fix with torch.compile(model, dynamic=True). (2) Graph breaks: Python control flow (data-dependent if, list comprehensions, calls to NumPy) splits the graph into many smaller subgraphs, each of which loses fusion opportunities. Diagnose with torch._dynamo.explain(model)(*args); fix by rewriting in pure tensor ops or wrapping with fullgraph=True to surface the breaks as errors. (3) Backend errors at first call: cuDNN or Triton kernels fail to compile for unusual shapes or dtypes. Diagnose with TORCHDYNAMO_VERBOSE=1; fall back to backend="aot_eager" or skip compile() for that submodule. The general practice from Section 0.3.7.1: profile with and without compile() on representative input, do not assume.
