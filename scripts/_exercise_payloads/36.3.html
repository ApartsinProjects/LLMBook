Exercise 36.3.1: Feasibility Before Demos Conceptual

Why does the order "feasibility -> demo -> investment" matter, and what goes wrong with the more common "demo -> investment -> feasibility" sequence? Give two concrete examples of LLM features that pass the demo gate and fail the feasibility gate.

Answer Sketch

Demos optimize for the spectator's experience (curated inputs, smooth narrative); feasibility studies optimize for the deployment's constraints (latency, cost, error tolerance, regulatory). Demo-first builds enthusiasm before anyone has measured whether the feature can actually meet its non-functional requirements; teams then commit budget to a project that is structurally infeasible. Examples: (1) "AI legal contract drafter" demos beautifully on a clean test contract but fails feasibility because hallucinated clauses are unacceptable risk and adding the verification layer doubles cost. (2) "AI medical pre-diagnosis chatbot" demos well but fails because the regulatory bar (FDA medical device approval) requires evidence quality the project cannot generate without years of clinical trials.

Exercise 36.3.2: Predict the Error-Tolerance Constraint Predictive

You're scoping an LLM feature with these per-task numbers: GPT-4 baseline accuracy 88%; user-acceptable error rate 5%. Predict: (a) the gap to close; (b) realistic levers and their typical magnitude; (c) when you should walk away from the project.

Answer Sketch

(a) Gap: 88% -> 95%, i.e., need to cut errors from 12% to 5%, a 2.4x reduction. (b) Realistic levers: prompt engineering (1-3 points typical), few-shot or RAG (3-8 points), small fine-tune (2-5 points on top), human-in-the-loop verification (turns most errors into edits, can effectively reach 99%+ task success). Combined, you can usually reach 92-96%. (c) Walk away if the gap can only be closed by HITL and the unit economics don't support a human reviewer per task; or if the residual 4-5% includes irreversible high-cost errors (medical advice, financial transactions). Both signal a role mismatch: the feature must change, not the model.

Exercise 36.3.3: Build a Feasibility Spike Code Tweak

Sketch a 1-day feasibility spike for "AI meeting action-item extractor." Specify (a) the dataset, (b) the metric, (c) the success threshold, (d) the no-go threshold, (e) the artifact you produce.

Answer Sketch

(a) Dataset: 30-50 real meeting transcripts with hand-labeled ground-truth action items. (b) Metric: per-meeting F1 of extracted action items vs. ground truth, plus a "human accept rate" if a reviewer eyeballs each output. (c) Success threshold: F1 >= 0.7 with a frontier model out of the box; this gives confidence prompt+RAG can push it to 0.85 in a real build. (d) No-go threshold: F1 < 0.4; this signals the task is harder than it looks (likely because action items are implicit/contextual) and the project needs a re-scope or more data work before commitment. (e) Artifact: a 1-page memo with the F1, qualitative error categories, cost-per-meeting estimate, and a recommendation. The whole spike costs ~$200 and saves 10x to 100x downstream waste on bad fits.

Exercise 36.3.4: Risk-Assessment Failure Modes Failure Mode

List three risks teams routinely under-weight in early LLM feasibility, and one cheap diagnostic for each.

Answer Sketch

(1) Data readiness: assumed corpora are dirtier or smaller than expected, blocking RAG/fine-tune later. Diagnostic: pull 100 real records and try to extract the target field manually; track time and ambiguity. (2) Latency budget: the demo runs in 5 seconds, but the use case needs 800 ms. Diagnostic: measure end-to-end latency under realistic prompt lengths and parallel load before committing. (3) Regulatory or contractual blockers: the data can't legally cross to a US-based API, or the customer's contract forbids ML use without disclosure. Diagnostic: legal pre-check on the top 3 customer accounts and the top 1-2 model providers in parallel with the technical spike. Each of these has killed real projects mid-build; one day spent up front saves months.
