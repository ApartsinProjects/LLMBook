# Module 06: Pre-training, Scaling Laws & Data Curation

**Audit date**: 2026-05-11
**Sections reviewed**: 6.1, 6.2, 6.3, 6.4, 6.5, 6.6, 6.7, 6.8
**Total word count**: ~38,000

## Summary
A strong, technically dense chapter that sweeps from the BERT/GPT/T5 lineage through pre-training objectives, Kaplan/Chinchilla scaling, MoE, optimizers, distributed training, ICL theory, and production training systems. Voice is consistent (a "Scale" agent narrates with witty asides) and the math is generally well-stated. The main weaknesses are a flood of broken or partial code captions, pervasive auto-rendering issues in math (e.g., `\masked` not a LaTeX command), several misnumbered figures, and section 6.8 substantially overlaps section 6.6 without explicit reconciliation.

## Inconsistencies
- **Cross-reference numbering drift.** Section 6.1 is constantly cross-referenced as "Chapter 04/Chapter 14/Chapter 23" etc. while the book is numbered with two-digit module IDs. E.g., 6.1 §"GPT-4 (2023)" links Chapter 23 for multimodal but the actual chapter is module-27. Section 6.4 quality-filter callout references Chapter 12 for synthetic data, but the actual location is module-13. Module-06 index links Chapter 14 for fine-tuning while the actual fine-tuning lives in module-14 (the same number, but referred to as "Chapter 13" elsewhere). Pick a numbering convention and apply it.
- **Figure numbering collisions.** In 6.1 the chapter-opener figure is "Figure 6.1.2" (line 49) and another image later is also "Figure 6.1.2" (line 117). In 6.3 multiple figures are all labeled "Figure 6.3.4" (lines 49, 65, 103, 123). In 6.5 two figures share label "Figure 6.5.3" (lines 51 and 192). 6.6 has two "Figure 6.6.3" instances (lines 49 and 91-100).
- **Code-caption duplication and corruption.** 6.1 has stacked captions: "Code Fragment 6.1.1" + "Code Fragment 6.1.8: [{'token_str': 'paris', 'score': 0.88}, ...]" (line 89). The second caption contains output, not a description. The file even includes a `<!-- FIXME: stacked caption, needs manual review -->` marker. 6.2 has "Code Fragment 6.2.1" followed immediately by "Code Fragment 6.2.9" (line 91). 6.3 has "Code Fragment 6.3.1" inserted between paragraphs that do not introduce code. 6.4 has "Code Fragment 6.4.8: pip install datasets" (line 257) which is a shell command, not a code fragment. 6.7 caption "Code Fragment 6.7.6: Define LinearAttentionAsGD; implement one_step_gd" (line 182) is template scaffolding text.
- **Cross-ref to §17.1 is repeated literally.** Many sentences read "...reinforcement learning from human feedback (Section 17.1), a technique we cover in depth in Section 17.1. The process had three stages: ... and optimizing the language model against that reward using Section 17.1." (6.1 §InstructGPT, line 165). The third occurrence should say "PPO". Same pattern recurs in 6.7 ("the same as gradient descent on a regression problem" but linking to §4.1 normalization).
- **§6.6 vs §6.8 overlap.** 6.8 opens with "6.6 covered what distributed training is. This section covers how production teams actually do it" but then re-explains TP/PP/DP/CP, Megatron-LM, FlashAttention, and FP8 (E4M3/E5M2) which are already in 6.6 and cross-referenced from 6.5. The split is artificial; 6.6 ends mid-FP8 explanation and 6.8 reopens it.
- **Inline auto-rendered LaTeX errors.** `$x_{\masked}$` and `$x_{\M}$` appear in 6.1 §BERT and 6.2.2 (lines 56, 59, 155, 158). `\masked` and `\M` are not LaTeX commands; KaTeX will throw. Should be `x_{\setminus M}` or similar.
- **Tokenization Code Fragment 7.4.1 inconsistency** (referenced from 6.x): note that several "Library Shortcut" callouts refer to Sections 14.5 / 15.x / 17.x as if all part-4 modules are interchangeable, breaking specificity.

## Gaps
- **No clear definition of "compute-optimal" before 6.3.4.** 6.3.4 calls it "the compute-optimal point for a single training run" but the deeper definition (jointly minimize L(N,D) under C ≈ 6ND) is asserted without showing the Lagrangian; the math `$N_opt \propto C^{0.5}$` is a result, not a derivation. A reader without grad-level optimization background cannot follow why exponents are 0.5.
- **6.3.7 MoE introduces gating without explaining how `top-K` is differentiable.** The auxiliary load-balance loss is shown but the straight-through estimator / Gumbel-softmax tricks that actually make `top-K` trainable are mentioned only obliquely ("The auxiliary loss is differentiable with respect to p_i...even though the hard selection of top-K experts is not itself differentiable"). The standard answer (gradients flow through the soft scores of selected experts, not through the selection itself) is missing.
- **6.5 promises "we'll cover grokking" and then gives one paragraph.** Grokking is mentioned in the index objectives ("training instabilities, grokking, loss landscape geometry") but only one paragraph of the section is devoted to it. No explanation of why it happens (weight-norm dynamics, regularization) or how to provoke it.
- **6.5.4 Muon promises a derivation that never arrives.** The text says Muon "applies orthogonalization to the momentum buffer at each step, projecting the update direction onto the Stiefel manifold" without any pseudocode or formula. Newton-Schulz iteration is the actual mechanism, not mentioned.
- **6.7 task-vector code is marked as "conceptual" then never replaced.** A `<div class="callout warning">` says "this code requires downloading a language model... not a standalone runnable script" (line 198). Nothing later in the section runs the extraction end-to-end on a real model.
- **6.8 Megatron table has no source for the parallelism configurations.** Llama 3.1 405B is cited as TP=8, PP=16, DP=128 but Meta's published config was TP=8, PP=16, DP=128, CP=8 (16,384 GPUs). The table omits CP for that row.
- **MTP appears in 6.2.6, 6.3.9, AND 7.2.4.4** with overlapping content. Each section is missing the cross-reference to the other two (only 6.2.6 → 7.2 is wired up; 6.3.9 silently re-introduces the same architecture).
- **6.3 promises "data-constrained scaling" and the Muennighoff result, then states the formula `D_eff = D_max(1 - e^{-R})`** without saying where the exponential comes from. The original paper fits a more complex form; the simplification needs justification or removal.

## Errors
- **6.1 §6.1.6 conflates Llama 3 8B with Llama 3 405B context.** "Llama 3 (2024) then pushed the open-weight frontier further with a 405B parameter model trained on 15 trillion tokens, achieving performance competitive with GPT-4 class systems." The 405B was trained on ~15.6T tokens (the 8B/70B were the baselines). Strictly correct, but the table at lines 311-316 lists "Llama 3 ... 8B / 70B / 405B ... 15T tokens" which is misleading because 15T applies to all three sizes (Meta did report this), so footnote it.
- **6.2 §6.2.2 standard MLM masking ratios.** "80% replaced by [MASK], 10% replaced by a random token, and 10% kept unchanged" (line 153) is correct, but the L_MLM formula uses `\sum_{i \in M}` summing over masked positions only - consistent with text. However, in 6.1 line 56 the same loss is written as `\Sigma _{t \in masked}` with `\masked` invalid. Math typo.
- **6.3.2 αN = 0.076, αD = 0.095, αC = 0.050.** These match the Kaplan paper. However the text then writes "doubling training compute yields a roughly 10% reduction in loss" - with αC ≈ 0.05, doubling C gives a factor of 2^{-0.05} ≈ 0.966, i.e. a 3.4% loss reduction. The stated "10%" is closer to what you'd get from a power-law-with-irreducible model after subtracting L_∞, but as written it's wrong.
- **6.3.3 Chinchilla "70B model trained on 1.4T tokens".** The actual Chinchilla model was 70B trained on 1.4T tokens, correct. But the text immediately says "20 tokens per parameter" - 70B × 20 = 1.4T, so consistent. Fine.
- **6.3.4 cites "Llama-1 7B was trained on 1 trillion tokens, giving a ratio of approximately 143 tokens per parameter, roughly 7x beyond the Chinchilla-optimal ratio."** 1T / 7B = 142.86, ratio is correct. 142.86 / 20 = 7.14, consistent.
- **6.3.5 `D_eff` formula.** The Muennighoff "data-constrained scaling laws" paper does not actually use `D_eff ≈ D_max(1 - e^{-R})`; it uses `D_eff = R + (R_*)(1 - e^{-R/R_*})` for repeated tokens and a separate term for parameters. The simplified version in the text is misleading; even the directionality is wrong (the actual paper says repeating up to ~4 epochs is nearly free, not exponentially decaying).
- **6.3.7 cites "Switch Transformers, Fedus et al. (2022)".** Correct year and authors.
- **6.3.7 MoE active params for DeepSeek V3.** "37B active parameters" - DeepSeek V3 paper reports 37.5B, close enough.
- **6.3.7 Mixtral 8x7B "47B total parameters"** - actually 46.7B, the section gets it right elsewhere as 46.7B (in 7.2.3) but rounds to 47B here.
- **6.4.1 pre-training data table.** "Wikipedia ~4B tokens (English)" - English Wikipedia is closer to 3-4B tokens depending on tokenizer, plausible.
- **6.4.4 Fun Fact: "250 billion web pages"** - Common Crawl has roughly 250 billion pages historically (cumulative across all snapshots), a single snapshot is 3-5B. The phrasing is fine if interpreted as cumulative.
- **6.5.2 Adam memory math.** "FP32... 7B parameter model thus needs approximately 112 GB" matches the code output (28+28+28+28). But the paragraph above says "Adam stores two extra values per parameter ... For a 70B parameter model, that is over 800 GB just for the optimizer states." 70B × 8 bytes (m+v in FP32) = 560 GB, not 800 GB. If you include parameters and gradients in FP32 (4+4), total state = 70B × 16 = 1120 GB. The "800 GB" figure is wrong - either it should be 560 GB (optimizer states only) or 1.12 TB (full state).
- **6.5.4 LION authors: "Chen et al., 2023".** Correct (Symbolic Discovery of Optimization Algorithms, Chen et al.).
- **6.5.5 cosine decay formula uses literal "½" and "−"** characters (line 199) instead of `1/2` and `-`, which renders inconsistently across browsers and fails KaTeX parsing in some configurations.
- **6.6.6 FP8 throughput comparison.** "989 TFLOPS of FP16 compute" on H100 - this is sparse FP16 TFLOPS; dense is ~756 TFLOPS for H100 SXM. The H100 FP8 figure of 3958 TFLOPS in 6.8.2.3 is the sparse number; dense FP8 is ~1979 TFLOPS. The chapter mixes sparse and dense numbers without flagging it.
- **6.7.3 attention-as-GD formula.** `$f(x_q) = W_V X^T X W_K^T W_Q x_q$` is the linear attention output but missing the value vectors V applied to the attended tokens; the Akyurek et al. derivation has it as `W_V Y^T (X^T X) W_K^T W_Q x_q` where Y are the in-context outputs. The formula as written treats X as both inputs and outputs.
- **6.8.1.2 Llama 3.1 405B claimed "approximately 30.8 million GPU-hours".** Meta's paper reports 30.84M H100-hours - correct. However the parallelism config "DP=128 (approximately)" in the same paragraph contradicts the table entry one block above which says DP=32, CP omitted. Reconcile.

## Improvements
- **Consolidate MTP coverage.** Currently in 6.2.6, 6.3.9, and 7.2.4.4. Choose one canonical location (6.2.6 makes sense as part of "objectives") and have the others just link.
- **Replace `Section 17.1` boilerplate.** Many sentences degenerate into "RLHF (Section 17.1), a technique we cover in Section 17.1, optimizing... using Section 17.1" - clearly an automated cross-ref expansion gone wrong. Audit pass to replace the third occurrence with "PPO" (or whatever the original noun was).
- **Fix figure numbering.** Use a script or naming convention so that no two figures share a number within a section.
- **Add a worked Lagrangian derivation for Chinchilla.** Show that minimizing `L(N,D) = E + A/N^α + B/D^β` subject to `C = 6ND` gives `N_opt ∝ C^{β/(α+β)}` and explain why with α≈0.34, β≈0.28 this is roughly C^0.45 (close to 0.5).
- **Show `top-K` gradient flow explicitly.** The MoE gradient question is a classic pedagogical gap. A two-line PyTorch snippet showing how the routing weights of the *selected* experts appear in the output (and thus the gradient flows through them) would close it.
- **Remove or rewrite the "FIXME" comment in 6.1** (line 97) which is exposed in the published HTML.
- **Caption hygiene pass.** Many code fragments have captions that are obviously templated ("Code Fragment X.Y.Z: pip install datasets" or "...: implement one_step_gd"). These should be human-readable descriptions of what the code does.
- **Clarify FP8 sparse vs dense TFLOPS** with a footnote in both 6.6 and 6.8.
- **Fix the 800 GB Adam fun-fact in 6.5.2** to either 560 GB (optimizer states alone) or 1.12 TB (full optimizer state including FP32 gradients and parameters).
- **6.8 should be merged into 6.6** or significantly trimmed. As written, 6.8 reads like a v2 of 6.6 with extra examples.

## One-thing-only fix
**Fix the recurring `Section 17.1`/`Section 4.1` cross-reference bug** that turns sentences like "the language model against that reward using Section 17.1" into nonsense. This pattern appears in dozens of places throughout Module 6 (and likely the rest of the book) and is the single change that would most improve readability for the affected paragraphs. The root cause appears to be an automated tool that replaced the noun (e.g., "PPO", "softmax", "layer normalization") with a hyperlinked section reference. A regex pass for `using Section X.Y` followed by manual review would fix it.
