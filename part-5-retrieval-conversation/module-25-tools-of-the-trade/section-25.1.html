Platforms

Section 25.1

The "platforms" of Part V are the managed and self-hosted vector databases. The vector database is where the embeddings live; everything else in a RAG system orbits around it.

25.1.1 Managed vector databases

  • Pinecone: the longest-running managed vector DB. Strong on operational ergonomics and hybrid (dense+sparse) search; per-namespace pricing.
  • Weaviate Cloud: open-source core with a managed offering; built-in modules for embedding generation.
  • Qdrant Cloud: Rust-based, high-performance; the right pick when latency matters.
  • MongoDB Atlas Vector Search and Azure AI Search: vector capabilities bolted onto existing managed databases. Best when your team already runs them.

25.1.2 Self-hosted and embedded

  • Chroma: embedded Python-first vector DB; default for prototypes.
  • FAISS: Facebook's vector library; the kernel that many other DBs use underneath.
  • pgvector: a Postgres extension. The right answer when "I already run Postgres" is true.
  • Milvus and its managed sibling Zilliz Cloud: distributed vector DB designed for billion-vector scale.
  • LanceDB: columnar embedded vector DB; new but gaining traction.

25.1.3 Comparing the platforms

25.1.1 Vector databases for Part V (as of 2026)
Database Deployment Strengths When not to use
Pinecone Managed only Hybrid search, ops Tight cost budgets
Chroma Embedded / self-host Dev ergonomics Billion-vector scale
Qdrant Self-host / cloud Latency, filtering Managed convenience
Weaviate Self-host / cloud Built-in modules Bare-bones use cases
pgvector Postgres extension Reuse existing DB Pure-vector workloads at scale

25.1.4 Choosing

For prototypes: Chroma. For small-to-medium production with existing Postgres: pgvector. For latency-sensitive search: Qdrant. For ops convenience: Pinecone. For billion-vector or multi-tenant SaaS: Milvus/Zilliz. The choice rarely matters at fewer than 1M vectors; it matters a lot at more than 100M.

Index type matters more than DB choice

All major vector DBs ship HNSW, IVF, and quantized indexes. The choice of index type and parameters usually determines recall and latency more than the choice of DB engine.
