Platforms

Section 6.1

Every line of code in Part I runs on top of a numerical computing platform: a runtime that owns the tensors, executes the kernels, and schedules work on CPU, GPU, or TPU. The platform decides what is fast, what is differentiable, and what is portable. For LLM work in 2026 the choices have consolidated, but they are not interchangeable.

6.1.1 PyTorch 2.x as the Default

PyTorch 2.x is the de facto standard for research and most production training. It owns roughly 90 percent of new public model releases on Hugging Face and is what every code listing in Chapters 0 through 5 assumes. Three things made PyTorch dominant: an eager imperative API that maps onto how researchers think, autograd that handles arbitrary control flow without graph rewrites, and (since 2.0) torch.compile which compiles hot regions with TorchInductor and Triton without forcing the user to rewrite anything.

For Part I you mostly use PyTorch's tensor primitives (torch.nn, torch.optim) and the autograd engine. The official documentation is well organized; the tutorials are good enough that we treat them as canonical reference. If you need to revisit the basics, Chapter 0 (ML and PyTorch Foundations) is the entry point and Appendix C covers the Python plumbing.

6.1.2 JAX When You Need XLA

JAX is Google's functional-style platform built on XLA. It is what you reach for when you need TPU performance, vmap-style batching, or aggressive ahead-of-time compilation. The mental model is different: pure functions, explicit PRNG keys, and a hard separation between Python and traced computation. Most LLM research outside of DeepMind still lands in PyTorch first; JAX-first releases (Gemma reference code, the MaxText training stack) are typically ported to PyTorch within weeks.

If you are doing capstone training runs on TPUs (Chapter 7) or large-scale pretraining (Chapter 21), JAX is worth learning. For Part I you can defer it.

6.1.3 NumPy and SciPy as the Numerical Substrate

NumPy still anchors data preprocessing, evaluation scripts, and most plotting pipelines. The 2.x API consolidation (NumPy 2.0 landed in mid-2024) removed many of the older idioms; tutorials older than 2024 may use deprecated patterns. SciPy sits one layer above for linear algebra extensions, signal processing, and statistical distributions you would not want to reimplement.

For practical work, treat PyTorch tensors as the primary container and convert to NumPy only when crossing into pandas, matplotlib, or scikit-learn boundaries. The conversion is cheap on CPU but expensive on GPU; tensor.cpu().numpy() is a synchronization point and is often the slowest line in a training loop you have not yet profiled.

6.1.4 scikit-learn for Classical ML

scikit-learn is not a deep learning library, but it remains the right answer for any baseline that is not an LLM. Logistic regression on TF-IDF features, random forests on hand-crafted features, k-fold evaluation, calibration plots, and confusion matrices are all one line. When you are debugging a fine-tuned model and you want to know whether a 0.78 F1 is good or bad, sklearn's baselines are the comparison.

6.1.6 Environment Notes

Install PyTorch with the CUDA build matched to your driver, not the latest available wheel. The official selector is the only source of truth; Stack Overflow answers older than a year are usually wrong about the right wheel. On Windows, prefer WSL2 for any serious training; native Windows works but the data loader is consistently slower. On Apple Silicon, the Metal backend (device='mps') handles forward passes and small fine-tunes but lacks coverage for some attention kernels; you will hit gaps the first time you run a recent paper.

Appendix D walks through reproducible environment setup with uv and pyproject.toml, including the lockfile patterns we use across the book. Appendix I covers the hardware side, including VRAM math and which GPUs are worth their price as of 2026.

Verifying the install

One-liner to confirm PyTorch sees your GPU: python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))". If the second value is empty or the call raises, fix the driver-CUDA-PyTorch triple before doing anything else. Spending an hour here saves a week of mysterious slowdowns.
